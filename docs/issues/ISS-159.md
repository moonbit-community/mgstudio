## Description
Bevy owns 3D camera projection types and behavior in
`bevy/crates/bevy_camera/src/projection.rs`. Mgstudio currently exposes
`Milky2018/mgstudio/camera/projection`, but that package is only a facade over
types and helpers still implemented under `Milky2018/mgstudio/pbr` and
`Milky2018/mgstudio/pbr/render`.

This owner split blocks source-level migration of
`bevy_light/src/cascade.rs::build_directional_light_cascades`: the Bevy system
belongs to the light owner but queries `Camera`, `Projection`, and
`GlobalTransform`. In mgstudio, importing the current 3D projection API from
`light` would create a local cycle through `camera -> pbr -> light`.

## Design
Move the Bevy-shaped 3D projection surface to the camera owner instead of
treating `pbr` as the canonical home. PBR may keep compatibility aliases only
after the canonical types, trait, constructors, matrix/frustum helpers, and ECS
component key live below camera-owned packages.

This is a local source-owner parity gap, not an external blocker. Do not add
fallback cascade code or a second projection abstraction to work around the
cycle.

## Acceptance Criteria
- [ ] `camera/projection` no longer aliases 3D projection types from `@pbr`.
- [ ] `PerspectiveProjection3d`, `OrthographicProjection3d`,
      `OrthographicScalingMode3d`, `SubCameraView3d`, `ProjectionMatrix3d`,
      `Projection`, `CustomProjection3d`, and `CameraProjection3d` have a
      camera-owned canonical implementation mapped to
      `bevy_camera/src/projection.rs`.
- [ ] PBR imports the camera-owned projection API instead of owning projection
      semantics itself.
- [ ] `light` can implement the Bevy-shaped
      `build_directional_light_cascades` entry point without importing PBR or
      creating a package cycle.
- [ ] Targeted release tests, `moon fmt`, `moon info`, native `moon check`, and
      a representative 3D lighting screenshot pass after the split.
