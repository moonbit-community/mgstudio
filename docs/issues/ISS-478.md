## Description

The transform gizmo was unported across all three of its source owners:

| mgstudio | before | Bevy owner | lines |
| --- | ---: | --- | ---: |
| `gizmos/transform_gizmo.mbt` | 15 | `bevy_gizmos/src/transform_gizmo.rs` | 768 |
| `gizmos_render/transform_gizmo_render.mbt` | 15 | `bevy_gizmos_render/src/transform_gizmo_render.rs` | 452 |
| `examples/gizmos/transform_gizmo/main.mbt` | 15 | `bevy/examples/gizmos/transform_gizmo.rs` | 180 |

All three were comment-only anchors.

Not externally blocked. The required capabilities all exist: `cylinder_mesh`,
`cone_mesh`, `torus_mesh` and `cuboid_mesh` in `mesh/primitives`, `RenderLayers`,
unlit `StandardMaterial`, `MeshPickingPlugin`, `Pickable`, `PointerButton`,
`FreeCamera`, `Window::cursor_position`, `CursorGrabMode::Confined`,
`camera_viewport_to_world_ray`, `camera_world_to_viewport`, `Ray3d`,
`Quat::from_axis_angle`, `Quat::from_rotation_arc` and
`Vec3::any_orthonormal_vector`. ISS-070's `Meshable` blocker concerns the
associated-builder type shape, not the ability to build these meshes: mgstudio
exposes free functions such as `cylinder_mesh(...)` instead of
`Cylinder::default().mesh().build()`.

## Progress

Ported so far in `gizmos/transform_gizmo.mbt`:

- all 18 constants and the four handle colours
- `TransformGizmoMode`, `TransformGizmoSpace`, `TransformGizmoAxis` with Bevy's
  `Default` variants
- `TransformGizmoFocus`, `TransformGizmoCamera`, `TransformGizmoRoot`,
  `TransformGizmoMeshMarker` components
- `TransformGizmoSettings` and `TransformGizmoState` resources with Bevy's
  default field values
- the `transform_gizmo_systems` system set and `TransformGizmoPlugin`
- the pure helpers: `axis_direction`, `translation_plane_normal`,
  `intersect_plane`, `point_to_segment_dist`, `effective_space`,
  `gizmo_rotation`, `snap_value`, `snap_axis`

12 whitebox tests in `gizmos/transform_gizmo_wbtest.mbt` cover the helper
semantics against the Bevy formulas, including the parallel-ray fallback to
`any_orthonormal_vector`, endpoint clamping in `point_to_segment_dist`, and the
rule that Scale mode always resolves to local space.

Also ported, in the `gizmos/transform_gizmo` fragment: `transform_gizmo_hover`,
`transform_gizmo_drag`, `resolve_gizmo_camera`, `point_to_ring_screen_dist` and
`TransformGizmoPlugin`, with Bevy's `PostUpdate` ordering (drag before
`transform_set_propagate`, hover after).

### Package cycle, and its root cause

The systems need camera viewport projection, and both
`camera_world_to_viewport` and `camera_viewport_to_world_ray` forwarded into
`pbr`, so importing either from `gizmos` closed the cycle

    light -> gizmos -> camera -> pbr -> ui_render -> ui -> text ->
    sprite_render -> sprite_render/render -> core_pipeline -> light

The first attempt pushed the *consumer* out of the way, into a
`gizmos/transform_gizmo` package. That compiled but left the real defect in
place. The defect is an ownership inversion: Bevy owns
`Camera::world_to_viewport` and `Camera::viewport_to_world` in
`bevy_camera/src/camera.rs`, and `bevy_pbr` depends on `bevy_camera`, never the
reverse. mgstudio had the math in `pbr/mesh_raycast.mbt` with `camera`
importing `pbr` to reach it.

Fixed by extracting the shared math into the leaf package
`camera/projection_math`, whose Bevy owner is `bevy_camera/src/camera.rs`. It
holds `camera_world_to_viewport`, `camera_viewport_to_world_ray`,
`camera_viewport_rect_logical`, `projection_runtime_projection`,
`projection_matrix_inverse`, `quat_rotate_vec3` and `quat_conjugate`, and
depends only on `math`, `transform`, `camera/camera` and `camera/projection3d`.
`pbr`, `pbr/render` and `camera` now all delegate to it, so there is one owner
rather than a copy plus a forward.

With the math in a leaf, `gizmos` reaches it without importing the `camera`
package at all, so the systems live in `gizmos/transform_gizmo.mbt` next to the
data model, where Bevy has them, and the split package is deleted.

Note that `camera -> pbr` still exists for 14 other symbols (`Projection`,
`Camera3dBundle`, `DepthOfField`, `AutoExposure`, decal and deferred config,
`render3d_camera_system`, `render3d_update_frusta_system`). That whole edge is
inverted against Bevy and remains open work.

## Example, and two bugs it found

`examples/gizmos/transform_gizmo` is ported and runs. Captured at frame 90
against the pinned Bevy example (built with `bevy_ci_testing,free_camera`):
mean_abs_rgb 41.96, 2251352 changed pixels.

What works: the gizmo renders. All three translate handles appear with Bevy's
colours -- magenta-pink X, green Y, blue Z -- plus the white view-plane circle,
with the correct shaft/cone shapes. That validates `spawn_gizmo_meshes`, the
render-layer-15 overlay camera, the colour table and the mesh primitives.

Two confirmed bugs, both open:

1. **The scene does not render.** Only the gizmo is visible; the ground plane,
   the table with its four legs, and the standalone cube are all missing.

   Narrowed by three experiments, each a fixed-frame capture against the same
   pinned Bevy baseline:

   | change | mean_abs_rgb | verdict |
   | --- | ---: | --- |
   | as committed | 41.95975 | baseline |
   | overlay camera `ClearColorConfig::None` | 41.95975 | byte-identical, ruled out |
   | `TransformGizmoPlugin` removed entirely | 41.99966 | scene still absent, ruled out |
   | scene materials forced `unlit` | 41.95975 | byte-identical, ruled out |

   The second row is the important one: with the gizmo plugin gone there is no
   overlay camera, no render layer 15 and no gizmo, and the scene *still* does
   not draw. **The defect is in the example's own scene setup, not in the
   transform gizmo render owner.** The third row rules out the lighting theory
   that the gizmo is visible only because its materials are `unlit`.

   Still to check: whether `@pbr.mesh_assets_mut_or_abort().modify(...)` inside
   an `add_systems_world(Startup, ...)` system registers handles the same way
   the working 3d examples do, and whether the degenerate `cuboid_mesh(10, 0, 10)`
   used for the ground plane is valid. `MeshMaterial3dBundle` already carries
   `layers`, `visibility`, `inherited_visibility` and `view_visibility` fields
   and the working 3d examples never set visibility by hand, so visibility and
   render layers are not obvious suspects.

2. **The gizmo is in the wrong place.** Bevy positions it on the focused table
   at `(-2, 1, 0)`; mgstudio draws it near the centre. Either
   `update_gizmo_meshes` is not reading the focus `GlobalTransform`, or the root
   transform is not propagating to the handle children.

The example also omits Bevy's instructions UI text (`Text` node plus the
per-frame mode/space readout). That is a deliberate gap, not a bug, and should
be added when the two above are fixed.

## Remaining
- Tests for `transform_gizmo_hover` and `transform_gizmo_drag`. These need a
  world with a camera, a primary window and injected cursor/mouse state, so
  they are a larger harness job than the pure-helper tests.
- `MIN_SCALE` and `snap_axis` are still `pub`. Now that the systems are back in
  the same package they can simply return to private.

## Render owner

`gizmos_render/transform_gizmo_render.mbt` is ported: the `GizmoOverlayCamera`
marker, the `TransformGizmoMaterials` normal/highlight/inactive colour table,
`spawn_gizmo_meshes` (cylinder shafts, cone tips, scale cubes, rotation tori,
view circle and view ring on render layer 15, plus the order-1 overlay camera)
and `update_gizmo_meshes`.

Two places where MoonBit forced a different expression, both behaviour-equal:

- Bevy compares `Color` values directly when deciding whether to rewrite a
  handle's base colour. mgstudio's `Color` has no `Eq`, so the srgba tuples are
  compared instead.
- Bevy reaches the material through `MeshMaterial3d<StandardMaterial>` deref;
  mgstudio rebuilds the handle with
  `@asset.Handle::from_asset_id(@asset.AssetId::new(component.material_asset_id()))`.

## Verification note

The transform gizmo is interactive: hover and drag depend on cursor position and
mouse buttons. A fixed-frame screenshot gate can validate the render path at
rest but cannot validate hover or drag. Those need either input injection in the
capture harness or a headless test that drives the systems directly.
