## Description

The first-ever pinned-Bevy spot capture of `examples/3d/tonemapping`
(frame 90, fixed frames, 2560x1440) shows our scene CONTENT diverging
structurally from Bevy's — mean_abs_rgb 52.34 against
`bevy/screenshot-90.png` — while the same-engine old-vs-new delta is the
clean expected tonemapping class (17.08 mean, matching the batch-1 packet
in reverse). The divergence is in what is being rendered mid-frame, not in
how it is tonemapped:

- Our capture and Bevy agree EXACTLY in the top-left UI text band
  (mean=52 std=34 bright_px=2176 on both) — the method/grading text
  returned with ISS-483's required-component fix and matches pinned Bevy.
- Mid-frame samples show different content classes at the same pixels,
  e.g. (1792,576) ours (79,130,164) bluish vs Bevy (156,80,113) magenta;
  (2048,288) ours (156,77,160) vs Bevy (236,228,215) near-white;
  (896,864) ours (95,105,78) vs Bevy (141,235,118) bright green;
  (512,288)/(1280,216) ours shows scene content where Bevy shows the dark
  backdrop.

Bevy's example cycles three scenes (keys 1-3) and displays an HDR test
image / color-sweep chart through an image viewer; the divergence pattern
suggests our port renders a different default scene state, a different
slide/chart, or different image-asset readiness at frame 90. Needs a
source-level diff of the example port plus asset-load-timing comparison
before any root-cause claim.

Human judgment (2026-08-04, VIS-481-batch1r): reference refresh HELD for
this example — the checked-in `reference.png` stays at the pre-ISS-483
state until this issue resolves, then it re-enters the ISS-481 sweep.
