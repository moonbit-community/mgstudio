## Description
`examples/3d/wireframe` now executes thin, wide, and quad-topology wireframes
from the dedicated retained `Wireframe3d` phase in a per-view Core3d
color/depth load-store pass. The old generated line-list regular-main-pass
surrogate, its GPU mesh cache, and the wireframe-config main-pass plumbing have
been deleted. Bevy owns a dedicated `WireframePlugin`,
`Wireframe3d` binned phase, thin and wide wireframe draw commands, specialized
wireframe pipelines, extracted render resources, and a `wireframe_3d` Core3d
node that runs after the main pass and before early postprocess.

The remaining implementation gaps are local source ownership, not external
backend blockers. They include the full Bevy batch-set/unbatchable execution
machinery, the GPU-building mesh-uniform owner, and replacing the
renderer-owned allocator mirror with the authoritative render-world owner.
The global extracted-view / visibility producer audit is tracked by ISS-018;
wireframe now consumes that shared producer instead of owning a duplicate.
Official-Bevy screenshot capture for the final human visual packet is tracked
separately by ISS-406.

## Design
Audit the Bevy source owner symbol by symbol before editing mgstudio. Every
source-shape anchor in `bevy_pbr/src/wireframe.rs` must be classified as
`complete`, `partial`, `blocked`, `facade`, or intentionally excluded. A local
approximation, bridge resource, renderer-owned mirror, or plan-only helper is
`partial` until the same Bevy owner consumes the data at runtime. Only a real
missing dependency, backend API, or MoonBit language limitation may be recorded
as `blocked`; project-local shortcuts must be replaced by source-shaped code.

## Source Owner Classification
- `bevy_pbr/src/wireframe.rs::Wireframe`, `NoWireframe`,
  `WireframeColor`, `WireframeLineWidth`, `WireframeTopology`,
  `WireframeConfig`: complete. Authoring data, change-driven main-world material
  application, and dedicated render-world phase consumption are connected
  without a generated-line-list main-pass path.
- `WireframeMaterial`, `RenderWireframeMaterial`,
  `RenderWireframeInstances`, `RenderWireframeAssets`: complete. Material data
  extraction and render asset mirroring feed both command tuples, including the
  exact 16-byte thin color block and 32-byte wide color/width/smoothing block.
- `WireframeEntitiesNeedingSpecialization`: complete for the Bevy dirty-source
  collection currently owned by
  `check_wireframe_entities_needing_specialization`. Component changes,
  component removals, `AssetChanged<Mesh3d>`, and
  `AssetChanged<Mesh3dWireframe>` are represented through typed ECS change /
  removal streams plus main-world `AssetEvent<Mesh>` and
  `AssetEvent<WireframeMaterial>` cursors.
- `DirtyWireframeSpecializations`, `PendingWireframeQueues`, `ViewKeyCache`:
  partial. The data owners and several Bevy helper semantics are present, but
  they are not yet consumed by a fully source-shaped `specialize_wireframes` /
  `queue_wireframes` chain, and shared camera/view dirty ownership remains
  incomplete.
- `Wireframe3d`, `Wireframe3dBatchSetKey`, `Wireframe3dBinKey`,
  `Wireframe3dPhases`: partial. The retained binned phase preserves cached bins
  across `prepare_for_new_frame`, and its thin items execute through the
  per-view Core3d `wireframe_3d` node. `UnbatchableMesh` entities now occupy
  real retained bins backed by the shared unbatchable index set, but the local
  phase does not yet materialize Bevy's full batch-set preparation or the
  source-scheduled per-frame unbatchable buffer lifecycle.
  `PhaseItemExtraIndex` and the phase item's `Range<u32>` representation now
  live in the shared `render/render_phase` owner and are consumed by both the
  wireframe and shadow phases instead of being duplicated in PBR. The shared
  owner also provides Bevy's nominal `InputUniformIndex`. The PBR
  `RenderMeshQueueData` producer now constructs that type at the same CPU/GPU
  queue-data boundary as pinned Bevy: CPU building returns the default index,
  GPU building wraps the raw flat-instance `u32`, and wireframe/shadow phases
  consume the nominal value directly. Raw integer conversion remains only at
  GPU-buffer/indexing boundaries. The shared owner also implements Bevy's
  `UnbatchableBinnedEntityIndexSet` sparse,
  dense, demotion-warning, lookup, add, and clear semantics; both shadow and
  wireframe consume it through real retained unbatchable bins. Bevy's
  shared `BinnedRenderPhaseType` and `mesh` classification helper also live in
  `render/render_phase`; wireframe, shadow, and prepass consume that owner.
  `MainEntity` now lives in the public `render/sync_world` leaf package and is
  re-exported by the root `render` package, removing the package-cycle obstacle
  to storing Bevy's `RenderBin` in the shared render-phase owner.
  The shared owner now contains Bevy's defaultable `RenderBin` with an ordered
  `MainEntity -> InputUniformIndex` index, replacement-in-place insertion,
  constant-time entity lookup, exact `swap_remove` deletion order, and the
  public read-only `entities` view. Its mutation methods remain private, as in
  Bevy. The generic `BinnedRenderPhase` owner has not yet been ported to consume
  those methods, so batchable wireframe storage and preparation remain partial;
  no placeholder phase-item synthesis or compatibility execution path was
  added in this slice.
  `RenderBinnedMeshInstanceIndex` and `RenderMultidrawableBin` now also live in
  the shared owner. The shadow multidraw path stores the nominal index against
  `MainEntity` directly, preserves the packed CPU/GPU-array swap-remove
  bookkeeping, and enforces Bevy's panic contract for missing bin keys, bins,
  indirect offsets, and entities. The generic `RenderMultidrawableBatchSet` and
  its
  `RenderMultidrawableBatchSetGpuBuffers` data owner now live in the shared
  render-phase package. The PBR shadow phase uses the real hashed `ShadowBinKey`
  as the generic key instead of a shadow-local `mesh_asset_id -> bin` map, and
  the shared owner performs stable bin allocation/reuse, tightly packed
  CPU/GPU instance bookkeeping, displaced-entity repair, indirect-parameter
  swap removal, and `u32::MAX` empty-slot marking. The shadow-specific
  containers, algorithms, and compatibility aliases have been deleted. The
  GPU-buffer owner remains partial because its current storage is a CPU array
  mirror rather than Bevy's uploaded/labeled `RawBufferVec` resources consumed
  by the bin-unpacking shader. The shared owner also contains Bevy's stable
  `RenderBinIndex`, raw GPU `GpuRenderBinnedMeshInstance`, and nominal CPU
  `CpuRenderBinnedMeshInstance` records. The shared batch set retains
  `RenderBinIndex` in its bin table, free list, indirect-offset reverse table,
  and CPU mirror, and unwraps it only at GPU-record construction or array
  indexing boundaries. The shadow-specific CPU/GPU record definitions have
  been deleted in favor of the shared types.
- `Wireframe3dPipeline`, `WireframePipelineKey`,
  `SpecializedWireframePipelineCache`,
  `SpecializedWireframeMeshPipelines`: complete. Source-shaped specialization
  data and descriptor rewriting consume the shared `MeshPipeline`,
  `RenderAssets<RenderMesh>`, and `PipelineCache` producer chain. The thin
  polygon-line pipeline and wide vertex-pulling pipeline are both consumed by
  the dedicated pass.
- `extract_wireframe_materials`, `extract_wireframe_3d_camera`: complete. They
  move real wireframe material data from the source world and prepare only the
  active retained camera phases, matching `wireframe.rs`. Wireframe
  specialization and queueing now read the shared `RenderVisibleEntities`
  Mesh3d class produced by the PBR prepare-meshes path; the wireframe-local
  duplicate producer and its duplicate visibility tests have been deleted.
  Remaining global `RenderExtractedVisibleEntities` / `RenderVisibleEntities`
  source-owner work belongs to ISS-018, not this wireframe source owner.
- `specialize_wireframes`, `queue_wireframes`: partial. System wrappers are
  registered and consume Bevy-shaped helper inputs, but this remains a local
  source-owner gap, not an external blocker. `RenderMeshInstances` is populated
  for the CPU-building path with Bevy-equivalent flags and default uniform
  indices, while the GPU-building path still lacks the source-shaped mesh
  uniform builder that assigns `current_uniform_index`. Per-entity visibility
  range dither and lightmap key derivation has been moved into specialization,
  and the PBR feature-plugin chain now installs the shared render-world
  `RenderVisibilityRanges` owner needed by the current wireframe consumer.
  Full source-owner parity still requires moving that installation back to the
  Bevy-equivalent `ViewPlugin` boundary after the current render/view package
  cycle is split.
  `RenderAssets<RenderMesh>` and `MeshPipeline` now feed specialization
  directly. `MeshAllocator` is still mirrored from the renderer backend instead
  of being the authoritative render-world resource.
- `DrawWireframe3dThin`, `DrawWireframe3dWide`,
  `SetWireframe3dWideBindGroup`, `SetWireframe3dThinImmediates`,
  `SetWireframe3dWideImmediates`, `DrawWireframeMeshPulled`,
  `wireframe_3d` Core3d graph node: complete for the command boundary. The thin
  tuple resolves the cached pipeline, binds mesh view/mesh resources, writes
  the 16-byte material immediate block, and issues the indexed mesh draw. The
  wide tuple binds group 3 with a dynamic vertex-pull parameter offset, writes
  the 32-byte immediate block, and issues direct or indirect non-indexed pulled
  draws inside the same per-view load/store pass.

## Acceptance Criteria
- [x] Every in-scope struct, resource, component, system, render command,
      pipeline key, and plugin hook in `bevy_pbr/src/wireframe.rs` is classified
      as complete, partial, blocked, facade, or intentionally excluded.
- [x] No anchor is counted complete only because mgstudio has a similarly named
      file, helper, bridge, or render plan; completion requires the Bevy owner
      to produce and consume the data at the same runtime boundary.
- [x] `WireframePlugin` installs Bevy-equivalent main-world and render-world
      resources and systems instead of only initializing `WireframeConfig`.
- [x] `Wireframe3d` is represented as its own render phase or an explicitly
      documented equivalent phase boundary, not as extra regular main-pass
      mesh draws.
- [x] Thin and wide wireframe pipeline specialization are ported or blocked
      with exact missing backend capability notes.
- [x] `examples/3d/wireframe` still captures a nonblank checked-in
      `reference.png` after the source-owner migration.
- [x] The old generated-line-list main-pass surrogate path is deleted once the
      dedicated `wireframe_3d` node owns actual drawing.
- [ ] Every remaining local `partial` source-owner classification above is
      completed or moved to a dedicated open issue with an exact relationship.
