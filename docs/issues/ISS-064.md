# ISS-064: Port Bevy Wireframe3d phase and pipeline source owners

## Metadata

## Description
`examples/3d/wireframe` now captures a usable reference, but mgstudio's 3D
wireframe implementation is still not source-level equivalent to Bevy's
`bevy/crates/bevy_pbr/src/wireframe.rs`. The current mgstudio path converts
triangle meshes into generated line-list meshes and draws them through the
regular PBR main pass. Bevy owns a dedicated `WireframePlugin`,
`Wireframe3d` binned phase, thin and wide wireframe draw commands, specialized
wireframe pipelines, extracted render resources, and a `wireframe_3d` Core3d
node that runs after the main pass and before early postprocess.

## Design
Audit the Bevy source owner symbol by symbol before editing mgstudio. Replace
the local generated-line-list approximation with Bevy-shaped ownership where
the current MoonBit renderer can express it. If an exact symbol requires a real
backend or language capability that does not exist, record that blocker
explicitly; do not classify local approximations as blockers.

## Source Owner Classification
- `bevy_pbr/src/wireframe.rs::Wireframe`, `NoWireframe`,
  `WireframeColor`, `WireframeLineWidth`, `WireframeTopology`,
  `WireframeConfig`: partial. Authoring data exists and the main-world
  material application path is present, but the full Bevy plugin ownership is
  not closed until the render-world phase consumes the resulting data without
  the legacy generated-line-list main-pass path.
- `WireframeMaterial`, `RenderWireframeMaterial`,
  `RenderWireframeInstances`, `RenderWireframeAssets`: partial. Material data
  extraction and render asset mirroring exist, but the full render command path
  does not yet bind them through Bevy-equivalent draw commands.
- `WireframeEntitiesNeedingSpecialization`: complete for the currently
  expressible dirty-source collection in
  `check_wireframe_entities_needing_specialization`. Component changes,
  component removals, `AssetChanged<Mesh3d>`, and
  `AssetChanged<Mesh3dWireframe>` are represented through typed ECS change /
  removal streams plus main-world `AssetEvent<Mesh>` and
  `AssetEvent<WireframeMaterial>` cursors.
- `DirtyWireframeSpecializations`, `PendingWireframeQueues`, `ViewKeyCache`:
  partial. The data owners and several Bevy helper semantics are present, but
  they are not yet consumed by a fully source-shaped `specialize_wireframes` /
  `queue_wireframes` chain, and shared camera/view dirty ownership remains
  incomplete.
- `Wireframe3d`, `Wireframe3dBatchSetKey`, `Wireframe3dBinKey`,
  `Wireframe3dPhases`: partial. The dedicated phase data owner exists and
  queue helpers can add/remove phase items, but execution is still not wired as
  a Core3d `wireframe_3d` node.
- `Wireframe3dPipeline`, `WireframePipelineKey`,
  `SpecializedWireframePipelineCache`,
  `SpecializedWireframeMeshPipelines`: partial. Source-shaped specialization
  data and descriptor rewriting exist, but the cache is not backed by a full
  Bevy `MeshPipeline` / `RenderMesh` / `PipelineCache` producer chain.
- `extract_wireframe_materials`, `extract_wireframe_3d_camera`,
  wireframe-visible camera extraction: partial. They now move real data from
  source world to render world, including render-entity visible Mesh3d pairs,
  but this is still wireframe-local. The shared Bevy `ExtractedCamera` /
  `ExtractedView` / `RenderVisibleEntities` owner must be migrated globally.
- `specialize_wireframes`, `queue_wireframes`: partial. System wrappers are
  registered and consume Bevy-shaped helper inputs, but this is a local
  source-owner gap, not an external blocker: `RenderMeshInstances` is populated
  for the CPU-building path with Bevy-equivalent flags and default uniform
  indices, while the GPU-building path still lacks the source-shaped mesh
  uniform builder that assigns `current_uniform_index`;
  `RenderAssets<RenderMesh>` pipeline data is not produced from the base
  `MeshPipeline`, and `MeshAllocator` is hidden inside the renderer backend
  instead of being a render-world resource.
- `DrawWireframe3dThin`, `DrawWireframe3dWide`,
  `SetWireframe3dWideBindGroup`, `SetWireframe3dThinImmediates`,
  `SetWireframe3dWideImmediates`, `DrawWireframeMeshPulled`,
  `wireframe_3d` Core3d graph node: partial. Immediate data structs exist, but
  the actual render command/node execution path is not yet source-equivalent.

## Acceptance Criteria
- [ ] Every in-scope struct, resource, component, system, render command,
      pipeline key, and plugin hook in `bevy_pbr/src/wireframe.rs` is classified
      as complete, partial, blocked, facade, or intentionally excluded.
- [ ] `WireframePlugin` installs Bevy-equivalent main-world and render-world
      resources and systems instead of only initializing `WireframeConfig`.
- [ ] `Wireframe3d` is represented as its own render phase or an explicitly
      documented equivalent phase boundary, not as extra regular main-pass
      mesh draws.
- [ ] Thin and wide wireframe pipeline specialization are ported or blocked
      with exact missing backend capability notes.
- [ ] `examples/3d/wireframe` still captures a nonblank checked-in
      `reference.png` after the source-owner migration.
