## Description
The latest 173 commits, from `a8e2ecca2 Refresh boxes3 reference capture`
through `5d1729cae Gate volumetric fog depth usage on lights`, cannot be
treated as a fully Bevy-faithful source migration set.

This audit intentionally ignores true external blockers when evaluating the
question. Even after excluding dependency/backend blockers, the commit set is
mixed: it contains implementation/parity work, reference screenshot refreshes,
tracker/blocker/classification updates, and local API cleanup. Those categories
are useful, but only the implementation commits can possibly count as Bevy
source migration, and even those still require source-owner symbol audits before
they can be certified complete.

Heuristic subject-line classification for the 173 commits:

- 82 commits are implementation or parity-shaped work, using subjects such as
  `Port`, `Align`, `Restore`, `Fix`, `Wire`, `Move`, `Prepare`, `Upload`,
  `Decode`, `Dispatch`, `Gate`, or `Skip`.
- 53 commits are reference screenshot refreshes.
- 21 commits are tracker, blocker, or classification updates.
- 17 commits are local API cleanup or local infrastructure changes, using
  subjects such as `Hide`, `Remove`, `Return`, `Rename`, or `Cache`.

The implementation group includes real Bevy-fidelity improvements, especially
in volumetric fog, SSAO, skybox, SSR, light probes, PCCM, decals, mixed
lighting, mirror, lightmaps, and example source-shape repairs. However, this is
not enough to certify the entire range as faithful: the recent volumetric fog
fixes themselves show that earlier states in the same range still had
source-behavior mismatches, such as depth-usage gating and missing-volume mesh
control flow.

## Design
Use this issue as the umbrella audit for the fixed commit range, not as another
implementation shortcut. Completion requires source-owner verification rather
than visual plausibility or commit-subject inference.

Required audit method:

- Pin the audited range to `a8e2ecca2..5d1729cae` inclusive, or update this
  issue explicitly if the range is intentionally changed.
- For every touched Bevy owner, list the Bevy source path first, then all
  mgstudio fragments implementing it.
- For each owner, classify every source-shape anchor as `complete`, `facade`,
  `partial`, or `blocked`.
- Treat screenshot refresh commits as evidence artifacts only, not source
  parity.
- Treat tracker/blocker commits as issue-tracker maintenance only, not source
  parity.
- Treat local API cleanup commits as parity risks until checked against the
  corresponding Bevy owner shape.
- Convert every local approximation, fallback, or implementation shortcut into
  a concrete source-parity issue. Do not classify local shortcuts as blockers.

Initial risk buckets discovered by this audit:

- Volumetric fog has the strongest implementation progress in this range, but
  it still needs final source-owner closure against
  `bevy_pbr/src/volumetric_fog/{mod.rs,render.rs}` before this range can be
  called complete.
- SSR, light probes, PCCM, skybox, SSAO, decals, mixed lighting, mirror,
  lightmaps, auto exposure, and morph targets each contain mixed implementation
  and reference evidence; each owner needs symbol-level verification.
- Reference screenshot refreshes must be reviewed separately from source
  migration. A valid capture does not prove Bevy source fidelity.
- Local visibility/API changes such as hiding constructors, removing facades,
  returning components directly, and caching composed WGSL may be correct, but
  they are not automatically Bevy-faithful without owner-shape checks.
