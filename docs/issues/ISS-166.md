# ISS-166: Queue mesh3d forward pipeline creation before draw execution

## Description
Mgstudio still has a renderer-local mesh3d forward pipeline path that can
create missing PBR render pipelines from inside draw execution. During
`examples/3d/transmission`, sampling shows the first draw call reaching
`mesh3d_pipeline_for_current_pass -> ensure_mesh3d_pipeline_surface ->
mesh3d_create_forward_shader_modules -> load_wgsl_preprocessed`, so the draw
path owns WGSL composition and render pipeline creation for missing forward
PBR variants.

This is a local source-owner boundary bug. Bevy specializes material mesh
pipelines before draw execution through `specialize_material_meshes`, stores
the resulting cached pipeline IDs in the retained-view specialized material
pipeline cache, and draw phase items consume those cached IDs. Draw commands
may observe pending or unavailable pipelines, but they must not create new
forward PBR shader modules as the normal missing-pipeline path.

## Design
Port the remaining local owner boundary to Bevy's source shape:

- Use Bevy source owners as the inventory:
  `bevy/crates/bevy_pbr/src/material.rs` for
  `specialize_material_meshes` / `queue_material_meshes`, and
  `bevy/crates/bevy_pbr/src/render/mesh.rs` for
  `MeshPipeline::specialize` descriptor ownership.
- Map the existing mgstudio fragments in `pbr/material_pipeline_specializer.mbt`,
  `pbr/material_specialization_ticks.mbt`, `pbr/render_execute_mesh_collect.mbt`,
  `pbr/render_execute_camera_main_pass.mbt`, and
  `render/renderer/mesh3d_pipeline_build.mbt`.
- Preserve `CachedRenderPipelineId` as the phase-item and draw-payload pipeline
  identity. If the pipeline is not materialized yet, skip or defer like Bevy's
  pending pipeline path instead of lazily composing WGSL in the draw function.
- Remove or shrink renderer-local forward pipeline creation once the
  render-resource descriptor path owns the same pipeline variants. Any
  remaining helper must be a materialization backend called from the cache
  owner, not a draw-time fallback.

Do not solve this by mutating WGSL, disabling feature defs, adding fallback
pipelines, increasing screenshot timeouts, or adding disk shader caches.

## Acceptance Criteria
- [ ] `mesh3d_pipeline_for_current_pass` either receives an already-selected
      cached pipeline or reports an explicit pending/unavailable state; it does
      not create the default forward PBR pipeline for a missing cache entry
      during draw execution.
- [ ] `render3d_execute_camera_main_pass` and mesh3d draw payloads consume the
      `CachedRenderPipelineId` selected by the material specialization/cache
      path.
- [ ] Missing or pending pipelines are represented explicitly and do not trigger
      draw-time WGSL composition.
- [ ] The source-shape inventory for the in-scope Bevy symbols is recorded in
      notes or close notes, with every symbol classified complete, partial, or
      blocked.
- [ ] Targeted render/PBR tests cover the pending-pipeline and cached-pipeline
      draw boundaries.
- [ ] A representative 3D/PBR example is run with the standard native capture
      command. If ISS-165 is still blocked by `moon_wgsl_naga_oil` performance,
      this issue may close on source/behavior tests while keeping screenshot
      parity blocked in ISS-165.

## Notes
- 2026-07-01: Created from ISS-165 diagnosis. This is the local Bevy-parity
  portion that remains actionable even while
  `moonbit-community/moon_wgsl#15` blocks full first-frame PBR shader compose
  performance.
- 2026-07-01: Ported the first main-pass draw consumption slice. Bevy source
  anchor `bevy_pbr/src/material.rs::queue_material_meshes` queues phase items
  with `CachedRenderPipelineId`, and `bevy_pbr/src/render/mesh.rs::DrawMesh`
  consumes the already-specialized phase item instead of creating pipelines.
  Mgstudio now registers successfully materialized `PipelineCache`
  `RenderPipeline`s in the renderer by cached material pipeline id, and
  `GpuBackend::draw_mesh3d_main_pass` uses that registered pipeline for
  non-default material ids. If the cached id has not materialized yet, main-pass
  draw returns pending instead of calling `mesh3d_pipeline_for_current_pass`.
  This classifies the main-pass non-default material draw boundary as
  `partial`: the ready/pending consumption behavior is source-shaped, but
  shadow, motion-vector, custom/default legacy paths, and full removal of the
  renderer-local forward pipeline owner still remain.
- 2026-07-01: Ported the matching shadow draw consumption slice. Bevy source
  anchor `bevy_pbr/src/render/light.rs::specialize_shadows` creates
  `CachedRenderPipelineId`s via `prepass_specialize`, and
  `queue_shadows` stores those ids in `ShadowBatchSetKey`; the `Shadow` phase
  item implements `CachedRenderPipelinePhaseItem` and draw consumes the cached
  pipeline. Mgstudio's `GpuBackend::draw_mesh3d_shadow_depth_pass` now treats
  non-default material pipeline ids the same way: it uses the renderer's
  materialized PipelineCache pipeline registration, and a missing registration
  is an explicit pending state rather than a draw-time call to
  `mesh3d_shadow_depth_pipeline_for_current_pass`. This classifies shadow
  non-default material draw as `partial`: the shadow cached-id consumption
  boundary is source-shaped, while default/depth-only legacy paths and the
  motion-vector owner remain local follow-up work.
- 2026-07-01: Ported the matching motion-vector/prepass draw consumption
  slice. Bevy source anchor `bevy_pbr/src/prepass/mod.rs` uses
  `specialize_prepass_material_meshes` to insert
  `(Tick, CachedRenderPipelineId, DrawFunctionId)` into
  `SpecializedPrepassMaterialPipelineCache`, then
  `queue_prepass_material_meshes` queues prepass/deferred phase items with
  that cached pipeline id; `DrawPrepass` consumes the already-selected item
  pipeline through `SetItemPipeline`. Mgstudio's
  `GpuBackend::draw_mesh3d_motion_vector_pass` now treats non-default material
  pipeline ids the same way: it uses the renderer's materialized
  `PipelineCache` pipeline registration plus the registered material layout,
  and a missing registration is an explicit pending state rather than a
  draw-time call to `mesh3d_build_motion_vector_pipeline`. This classifies the
  non-default motion-vector/prepass material draw boundary as `partial`: cached
  pipeline consumption is source-shaped, while the default legacy
  motion-vector pipeline path and full Bevy prepass phase ownership remain
  follow-up work.
- 2026-07-01: Tightened the main-pass queue invariant. Bevy
  `queue_material_meshes` requires `ResMut<SpecializedMaterialPipelineCache>`;
  the system cannot legally run without the retained-view pipeline cache, and
  a missing view cache means the entity is skipped rather than sent to draw with
  a default pipeline. Mgstudio's real `render3d_queue_meshes_system` now treats
  a missing `SpecializedMaterialPipelineCache` resource as an initialization
  error instead of passing `None` into the camera queue builder. This classifies
  the real queue-system cache ownership as `partial`: runtime queue execution
  now requires the Bevy-shaped cache resource, while test helper overloads and
  the legacy `ExtractedMesh3d.material_pipeline_id` fallback remain follow-up
  source-owner cleanup.
- 2026-07-01: Removed the queue-helper fallback called out above. Mgstudio's
  `render3d_queue_mesh_phase_items` CPU and GPU-builder paths now require a
  retained-view entity plus `SpecializedMaterialPipelineCache`, look up the
  cached pipeline id from that cache, and skip meshes with missing cache
  entries. `MeshPhaseItem3d.pipeline_id` is now a required
  `CachedRenderPipelineId`, matching Bevy's phase item shape where
  `queue_material_meshes` inserts a concrete `pipeline` id and draw consumes
  that selected id. The remaining ISS-166 partials are now below this boundary:
  default renderer-local forward pipeline creation and full removal/rehome of
  the renderer-local materialization backend.
- 2026-07-01: Removed another legacy compatibility data path from the PBR
  specialization owner. `render3d_prewarm_mesh_pipelines` now only specializes
  the material pipeline and records the result in
  `SpecializedMaterialPipelineCache`; it no longer writes the returned
  `CachedRenderPipelineId` back into `ExtractedMesh3d.payload.material_pipeline_id`.
  The extracted payload field has been removed entirely, so extracted meshes no
  longer carry a second optional pipeline identity alongside the retained-view
  cache.
  This keeps `queue_material_meshes` parity on a single source-shaped pipeline
  identity path: retained-view cache entry to phase item to draw payload.
  Remaining partials are the lower renderer-local default/custom pipeline
  materialization helpers and the optional `material_pipeline_id` on the final
  GPU draw payload builder.
- 2026-07-01: Made the final PBR GPU draw payload pipeline identity required.
  `MeshGpuDrawPayload3d.material_pipeline_id` and
  `render3d_build_mesh_gpu_draw_payload` now require a concrete
  `CachedRenderPipelineId`; main-pass, shadow, motion/prepass, and meshlet
  material shade callers pass the cached id they selected. The motion/prepass
  path now skips the draw when `render3d_prewarm_prepass_material_pipeline`
  returns `None`, matching Bevy's pending-pipeline skip behavior instead of
  constructing a draw payload with no pipeline identity. The only explicit
  invalid id call site is the separate wireframe overlay path, which belongs to
  the wireframe owner rather than Bevy's PBR material queue owner and remains a
  separate parity audit target.
- 2026-07-01: Removed the draw-time main-pass fallback to
  `mesh3d_pipeline_for_current_pass`. `GpuBackend::draw_mesh3d_main_pass` now
  only consumes an already-registered material render pipeline for the
  `CachedRenderPipelineId` carried by the draw payload; missing registrations,
  including the legacy default/invalid id, are treated as pending and skipped.
  This matches Bevy's `SetItemPipeline` behavior for
  `CachedRenderPipelinePhaseItem`: draw execution observes `PipelineCache`, but
  does not create forward PBR shader modules.
