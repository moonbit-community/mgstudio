## Description
`ISS-153` classified mesh preparation source anchors and split the remaining
implementation into this issue. `ISS-155` is the active local migration issue
for the boundary where Bevy's render mesh owner feeds Bevy's PBR material
owner. It is not a general "PBR is unfinished" bucket, not only a
`many_foxes` performance issue, and not only a GPU-building data-structure
issue.

The Bevy source anchors are:

- `bevy_pbr/src/render/mesh.rs`: `RenderMeshInstances`,
  `extract_meshes_for_cpu_building`, `extract_meshes_for_gpu_building`,
  `collect_meshes_for_gpu_building`, `collect_gpu_culled_meshes`, and
  `set_mesh_motion_vector_flags`.
- `bevy_pbr/src/material.rs`: `Material`, `MaterialPlugin<M>`,
  `PreparedMaterial`, `RenderMaterialInstances`, `RenderMaterialBindings`,
  `specialize_material_meshes`, `queue_material_meshes`,
  `DirtySpecializations`, and `PendingMeshMaterialQueues`.
- `bevy_pbr/src/lib.rs`: `PbrPlugin` installs
  `MaterialPlugin::<StandardMaterial>` directly. Bevy does not have a separate
  `StandardMaterialPlugin` owner that bypasses the generic material path.

Mgstudio already has many Bevy-shaped fragments and white-box tests for these
anchors. The issue remains open because the runtime still crosses this boundary
through the legacy `ExtractedMesh3d` / `Mesh3dExtractedPayload` adapter in
important places. That adapter still conflates extraction, material resolution,
texture bind group preparation, material specialization inputs, phase queueing,
and backend draw payload construction. Full parity means the Bevy owner path
itself must produce, update, specialize, queue, and consume mesh/material data
in the render world.

Recent material-owner slices moved generic material preparation closer to
Bevy's `MaterialPlugin<M>` path: renderer-method resolution now happens at the
prepared-asset boundary, generic material layout/key/data hooks exist, and
`StandardMaterial` now has a first generic `Material` surface whose non-bindless
binding payload carries the Bevy-shaped `StandardMaterialUniform` plus Bevy's
full binding-number surface through binding 30. Material preparation also now
receives `RenderAssets<GpuImage>` metadata so `TWO_COMPONENT_NORMAL_MAP` is
derived from the actual normal-map texture format like Bevy's
`AsBindGroupShaderType<StandardMaterialUniform>`. These are prerequisites, not
closure. The remaining specialization and queue runtime still adapt from the
old extracted-mesh payload instead of using the Bevy material and render-mesh
resources as source of truth, and the corresponding feature shader defs and
pipeline-layout runtime paths still need source-level migration.

The issue should be read as a source-of-truth migration issue, not as a hook
inventory. Adding another generic hook, prepared-material field, or consumer
adapter only counts for the source anchor it directly ports. The issue remains
open until the runtime specialization and queue paths read Bevy-shaped
`RenderMeshInstances`, `RenderMaterialInstances`, `RenderMaterialBindings`,
prepared materials, and render mesh assets as their authoritative inputs.

Do not describe another consumer-side slice as full parity. A slice is complete
only for the exact source anchor it covers. If a local approximation remains,
classify it as partial local migration work; do not label it as an external
blocker.

Current source-shape classification for the most recent StandardMaterial owner
slice:

- `bevy_pbr/src/lib.rs::PbrPlugin` installing
  `MaterialPlugin::<StandardMaterial>`: complete for owner routing. Mgstudio's
  `PbrPlugin` now delegates StandardMaterial asset/render-asset extraction,
  preparation, allocator setup, and runtime registration through the generic
  `MaterialPlugin<StandardMaterial>` path.
- `mgstudio_pbr::StandardMaterialPlugin`: facade/config wrapper. Bevy has no
  separate `StandardMaterialPlugin` owner. This wrapper must not be counted as
  a complete Bevy source owner; it exists only to preserve the current mgstudio
  configuration surface while forwarding the real work to generic
  `MaterialPlugin<StandardMaterial>`.
- `Material::register_shader_sources`: MoonBit-local adaptation. Bevy does not
  have this trait method. It preserves the Bevy ownership rule that
  StandardMaterial's built-in PBR shader libraries are loaded by `PbrPlugin`,
  while custom material shader assets can still be registered by generic
  material plugins. Do not count this hook as source-complete Bevy API; it is
  acceptable only as a local expression of a Bevy owner boundary.

## Design
Port Bevy's owner shape directly and keep source-anchor ownership explicit:

- Replace the single-map `RenderMeshInstances` facade with a source-shaped
  `CpuBuilding` / `GpuBuilding` representation.
- Port `extract_meshes_for_gpu_building` changed-query semantics as closely as
  MoonBit ECS allows, recording a smaller blocker if query filters or removed
  component readers cannot express the source shape.
- Port `RenderMeshInstanceGpuQueue`, `RenderMeshInstanceGpuBuilder`,
  `RenderMeshInstanceGpuPrepared`, and `MeshesToReextractNextFrame`.
- Move mesh instance preparation out of the monolithic
  `render3d_extract_mesh_for_entity` / `render3d_execute_collect_meshes` path.
- Keep `RenderMeshAssets` and `MeshAllocator` as authoritative render-world
  resources instead of using host upload cache state as a substitute.
- Move StandardMaterial onto the same generic material owner shape as Bevy:
  `PbrPlugin` should be able to install `MaterialPlugin<StandardMaterial>` or a
  MoonBit-equivalent direct mapping, rather than relying on a separate
  standard-material-only owner that hides generic material gaps.
- Move `specialize_material_meshes` inputs off `ExtractedMesh3d` and onto
  `RenderMeshInstances`, `RenderMaterialInstances`, `RenderMaterialBindings`,
  prepared material assets, retained views, and render mesh assets.
- Move `queue_material_meshes` off stale extracted payload state. Missing
  specialization cache entries, missing mesh/material resources, and pending
  retry behavior must match Bevy's queue semantics.

Do not add dirty-skip shortcuts, fallback pipelines, or standard-material-only
shortcuts that alter Bevy-visible mesh or material semantics.

## Acceptance Criteria
- [x] `RenderMeshInstances` has Bevy-shaped CPU and GPU building variants.
- [x] GPU mesh instance extraction records changed, removed, and reextract-next
      frame entities through source-shaped resources or documented blockers.
- [x] Mesh instance preparation consumes `MeshAllocator`, material bindings,
      lightmaps, skin uniforms, morph indices, and frame count in the Bevy
      owner path.
- [x] GPU-culling visibility state is collected into camera and shadow-map
      `RenderVisibleEntities`, matching Bevy's
      `collect_gpu_culled_meshes` owner slice.
- [x] `DirtySpecializations`, retained-view specialization caches, and
      pending material queues exist as Bevy-shaped resources.
- [x] Material specialization work items carry Bevy-shaped fields before the
      pipeline specialization/cache write step.
- [x] `StandardMaterial` is routed through the generic Bevy material owner
      shape, or a precise MoonBit language/API blocker states why that exact
      owner cannot be expressed yet.
- [x] `StandardMaterial` generic preparation no longer uses the
      placeholder/default bind group for the currently enabled non-bindless
      StandardMaterial binding surface.
- [x] `StandardMaterial` generic preparation receives render image metadata
      needed to set Bevy's `TWO_COMPONENT_NORMAL_MAP` uniform flag.
- [x] `StandardMaterial` authoring fields and generic bind-group payload cover
      the Bevy non-bindless texture binding-number surface through binding 30.
- [x] PBR specialization and runtime layout paths enable and consume Bevy's
      corresponding feature shader defs for transmission, multi-layer, and
      specular textures with the same semantics as Bevy.
- [x] `specialize_material_meshes` no longer consumes
      `ExtractedMesh3d` / `Mesh3dExtractedPayload` as its source of truth.
- [ ] `queue_material_meshes` consumes Bevy-shaped render mesh/material
      resources and skips/pends entities with the same semantics as Bevy.
- [ ] The monolithic PBR collect path no longer owns mesh upload/cache and mesh
      instance preparation together.
- [ ] `many_foxes` reports `mgstudio.render.prepare_meshes < 1 ms/frame` at
      `1000` foxes on the current development machine, or a more specific ECS
      blocker is recorded with exact evidence.
- [x] Relevant `mesh`, `pbr/render`, and `pbr` release tests pass.
