## Description
`ISS-153` classified mesh preparation source anchors. This issue now tracks the
remaining source-owner migration that sits between Bevy's render mesh owner and
Bevy's PBR material owner. It is not only a `many_foxes` performance issue and
not only a GPU-building data-structure issue.

The Bevy source anchors are:

- `bevy_pbr/src/render/mesh.rs`: `RenderMeshInstances`,
  `extract_meshes_for_cpu_building`, `extract_meshes_for_gpu_building`,
  `collect_meshes_for_gpu_building`, `collect_gpu_culled_meshes`, and
  `set_mesh_motion_vector_flags`.
- `bevy_pbr/src/material.rs`: `Material`, `MaterialPlugin<M>`,
  `PreparedMaterial`, `RenderMaterialInstances`, `RenderMaterialBindings`,
  `specialize_material_meshes`, `queue_material_meshes`,
  `DirtySpecializations`, and `PendingMeshMaterialQueues`.
- `bevy_pbr/src/lib.rs`: `PbrPlugin` installs
  `MaterialPlugin::<StandardMaterial>` directly. Bevy does not have a separate
  `StandardMaterialPlugin` owner that bypasses the generic material path.

Mgstudio already has many Bevy-shaped fragments and white-box tests for these
anchors, but the issue remains open because the runtime is still partly fed by
the legacy `ExtractedMesh3d` / `Mesh3dExtractedPayload` adapter. That adapter
still conflates extraction, material resolution, texture bind group
preparation, material specialization inputs, phase queueing, and backend draw
payload construction. Full parity means the Bevy owner path itself must
produce, update, specialize, queue, and consume mesh/material data in the render
world.

Do not describe another consumer-side slice as full parity. A slice is complete
only for the exact source anchor it covers. If a local approximation remains,
classify it as partial local migration work; do not label it as an external
blocker.

## Design
Port Bevy's owner shape directly and keep source-anchor ownership explicit:

- Replace the single-map `RenderMeshInstances` facade with a source-shaped
  `CpuBuilding` / `GpuBuilding` representation.
- Port `extract_meshes_for_gpu_building` changed-query semantics as closely as
  MoonBit ECS allows, recording a smaller blocker if query filters or removed
  component readers cannot express the source shape.
- Port `RenderMeshInstanceGpuQueue`, `RenderMeshInstanceGpuBuilder`,
  `RenderMeshInstanceGpuPrepared`, and `MeshesToReextractNextFrame`.
- Move mesh instance preparation out of the monolithic
  `render3d_extract_mesh_for_entity` / `render3d_execute_collect_meshes` path.
- Keep `RenderMeshAssets` and `MeshAllocator` as authoritative render-world
  resources instead of using host upload cache state as a substitute.
- Move StandardMaterial onto the same generic material owner shape as Bevy:
  `PbrPlugin` should be able to install `MaterialPlugin<StandardMaterial>` or a
  MoonBit-equivalent direct mapping, rather than relying on a separate
  standard-material-only owner that hides generic material gaps.
- Move `specialize_material_meshes` inputs off `ExtractedMesh3d` and onto
  `RenderMeshInstances`, `RenderMaterialInstances`, `RenderMaterialBindings`,
  prepared material assets, retained views, and render mesh assets.
- Move `queue_material_meshes` off stale extracted payload state. Missing
  specialization cache entries, missing mesh/material resources, and pending
  retry behavior must match Bevy's queue semantics.

Do not add dirty-skip shortcuts, fallback pipelines, or standard-material-only
shortcuts that alter Bevy-visible mesh or material semantics.

## Acceptance Criteria
- [x] `RenderMeshInstances` has Bevy-shaped CPU and GPU building variants.
- [x] GPU mesh instance extraction records changed, removed, and reextract-next
      frame entities through source-shaped resources or documented blockers.
- [x] Mesh instance preparation consumes `MeshAllocator`, material bindings,
      lightmaps, skin uniforms, morph indices, and frame count in the Bevy
      owner path.
- [x] GPU-culling visibility state is collected into camera and shadow-map
      `RenderVisibleEntities`, matching Bevy's
      `collect_gpu_culled_meshes` owner slice.
- [x] `DirtySpecializations`, retained-view specialization caches, and
      pending material queues exist as Bevy-shaped resources.
- [x] Material specialization work items carry Bevy-shaped fields before the
      pipeline specialization/cache write step.
- [ ] `StandardMaterial` is routed through the generic Bevy material owner
      shape, or a precise MoonBit language/API blocker states why that exact
      owner cannot be expressed yet.
- [ ] `specialize_material_meshes` no longer consumes
      `ExtractedMesh3d` / `Mesh3dExtractedPayload` as its source of truth.
- [ ] `queue_material_meshes` consumes Bevy-shaped render mesh/material
      resources and skips/pends entities with the same semantics as Bevy.
- [ ] The monolithic PBR collect path no longer owns mesh upload/cache and mesh
      instance preparation together.
- [ ] `many_foxes` reports `mgstudio.render.prepare_meshes < 1 ms/frame` at
      `1000` foxes on the current development machine, or a more specific ECS
      blocker is recorded with exact evidence.
- [x] Relevant `mesh`, `pbr/render`, and `pbr` release tests pass.
