# ISS-006: Remove redundant joint work from skin extraction

## Description
Skin extraction costs about `5.652 ms/frame` in the main system and
`5.619 ms/frame` in the render queue. It walks many joints and writes staging
data every frame for animated skins.

## Design
Align skin extraction with Bevy's dirty-skin collection and staging-buffer
semantics. The optimized path should have strong invariants for skin metadata,
direct staging indexing for joint matrices, and no hot-loop repair fallback.

## Acceptance Criteria
- [x] Skin extraction is split into add/delete handling, joint extraction, staging writes, and upload preparation spans.
- [x] The report records skins, joints, dirty skins, staging rows, and upload bytes.
- [x] Per-frame metadata repair paths are removed from the hot loop once invariants are established.
- [x] Joint transform fetch state is shared with or made consistent with skinned-bounds fetch state where source-equivalent.
- [x] At `1000` foxes, skin extraction is reduced below `2.5 ms/frame` or a follow-up issue documents the remaining blocker.
- [x] Relevant PBR skinning tests pass with `--release`.

## Notes
- Current evidence: `extract_3d_skins=5.619 ms/frame`.
- 2026-06-04: Bevy `bevy_pbr/src/render/skin.rs` does not build a local dirty-skin threshold or fall back to rewriting every joint for every prepared skin. It iterates every `SkinnedMesh`, skips skins already initialized by the changed-skinned-mesh query, then writes only joints whose `GlobalTransform` is in `Changed<GlobalTransform>`.
- 2026-06-04: mgstudio now mirrors that source shape: `render3d_add_or_delete_skins` initializes changed skins, and `render3d_extract_joints_for_skin` skips unchanged joint transforms and writes changed joint rows directly.
- 2026-06-04: many_foxes still changes all `24000` joint global transforms per sampled frame, so source-equivalent extraction still writes all joint rows. The latest profile reports `extract_3d_skins=2.703 ms/frame`, `pbr.skin_extraction.joints=24000`, and `pbr.skin_extraction.joint_transform_cache_hits=24000`.
- 2026-06-04: The remaining sub-`2.5 ms/frame` target is tracked in ISS-042 because it requires lower-level hot-path work beyond the source-shape bug fixed here.
