## Description
The failed `volumetric_fog` frame can still come from a main opaque pass
ordering or depth/load-state mismatch: skybox, opaque meshes, atmosphere, and
the volumetric fog pass must be ordered like Bevy and must use compatible depth
and color attachment state.

Audit this pass boundary before changing renderer code.

## Design
Compare Bevy's `MainOpaquePass3dNode` and related Core3d ordering against
mgstudio's camera main-pass execution. Classify where these actions occur:
skybox draw, opaque phase draw, gizmo draw, atmosphere sky draw, main pass end,
and volumetric fog pass start.

If mgstudio differs, create or implement the source-shaped fix in the owning
fragment. Do not move draws based only on visual intuition; cite the Bevy owner
and preserve its ordering semantics.

## Close Notes
Closed as a source-level audit. No renderer code was changed for this issue.

Bevy source anchors:

- `bevy/crates/bevy_core_pipeline/src/core_3d/main_opaque_pass_3d_node.rs`
  opens `main_opaque_pass_3d` with one color attachment from
  `ViewTarget::get_color_attachment()` and one depth attachment from
  `ViewDepthTexture::get_attachment(StoreOp::Store)`.
- In that pass, Bevy renders opaque phase first, alpha-mask phase second, then
  skybox last. Skybox draws only when both `SkyboxPipelineId` and
  `SkyboxBindGroup` are present.
- `bevy/crates/bevy_core_pipeline/src/skybox/mod.rs` specializes the skybox
  pipeline with `depth_write_enabled: false` and
  `CompareFunction::GreaterEqual`, using `CORE_3D_DEPTH_FORMAT`.
- `bevy/crates/bevy_core_pipeline/src/core_3d/mod.rs` installs
  `(main_opaque_pass_3d, main_transparent_pass_3d).chain()` in
  `Core3dSystems::MainPass`.
- `bevy/crates/bevy_pbr/src/atmosphere/mod.rs` schedules
  `(atmosphere_luts, atmosphere_environment).chain()`
  after `Core3dSystems::Prepass` and before `Core3dSystems::MainPass`, and
  schedules `render_sky.after(main_opaque_pass_3d).before(main_transparent_pass_3d)`.
- `bevy/crates/bevy_pbr/src/atmosphere/node.rs::render_sky` opens a separate
  color-load render pass labeled `render_sky` with no depth attachment.
  Its shader samples the view depth texture through bind group binding 13.

Mgstudio fragments:

- `mgstudio-engine/pbr/render_execute_camera_main_pass.mbt` opens the 3D main
  pass through `@pbr_render.render3d_begin_pass_3d`, builds the main binned
  phase, draws the mesh GPU-binned phase, draws gizmo lines, then calls
  `@core_pipeline.main_opaque_pass_3d_draw_skybox`.
- `mgstudio-engine/render/renderer/pass_begin.mbt` opens the corresponding
  color/depth pass with color store and depth store operations set to
  `STORE_OP_STORE`; depth clears to `0.0`, matching the reverse-Z convention
  used by the local PBR path.
- `mgstudio-engine/render/renderer/gpu_skybox.mbt` builds the skybox pipeline
  with depth write disabled and `COMPARE_FUNCTION_GREATER_EQUAL`, matching the
  Bevy skybox depth state.
- `mgstudio-engine/pbr/render_execute_camera_main_pass.mbt` calls
  `@render.host_gpu_draw_mesh3d_atmosphere_sky` when the camera has atmosphere.
  Although this call appears before the explicit main-pass end, the backend
  implementation in `mgstudio-engine/render/renderer/gpu_atmosphere.mbt`
  first calls `mesh3d_end_active_pass_preserving_state`, then opens a
  color-load render pass, draws the atmosphere sky fullscreen triangle, and
  reopens the saved pass state.
- `mgstudio-engine/pbr/atmosphere/render_sky.wgsl` is byte-identical in the
  audited region to Bevy's `render_sky.wgsl`: it samples binding 13 as the
  depth texture and branches on `depth == 0.0`.

Audit conclusion:

- The current `volumetric_fog` near-grey frame is not explained by a missing
  skybox draw in the main opaque pass, by skybox being drawn before opaque
  meshes, or by a skybox depth-write/compare mismatch.
- The apparent atmosphere call-site difference is an ownership/source-shape
  issue: Bevy owns `render_sky` as a Core3d system after
  `main_opaque_pass_3d`, while mgstudio currently invokes it from the PBR
  camera execution path. The backend still performs a separate color-load pass
  with no depth attachment, so this audit does not identify it as the direct
  cause of the near-grey frame. The broader atmosphere/Core3d ownership gap is
  already related to ISS-065.
- The remaining likely local boundary for this `volumetric_fog` failure is
  skybox shader/cubemap sampling/exposure parity, tracked by ISS-349.
