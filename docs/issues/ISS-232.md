## Description
`scrolling_fog` can have correct directional shadow visibility while still
failing before Bevy's `specialize_shadows` pipeline work if the visible entity
does not resolve to the required render material instance, render mesh
instance, material asset, mesh asset, or shadow-caster flag. This issue isolates
that input boundary.

## Design
Audit Bevy `bevy_pbr/src/render/light.rs::specialize_shadows` for the
material/mesh/resource lookups that happen before creating
`ShadowSpecializationWorkItem`. Compare those lookups against mgstudio's
`render3d_shadow_specialization_queue_data` and the `scrolling_fog` pillar
path. Fix local divergences source-faithfully. Do not make shadow queueing
accept incomplete inputs.

## Acceptance Criteria
- [x] The `scrolling_fog` pillar visible entity resolves to a render material
      instance.
- [x] The same entity resolves to a render mesh instance with the
      `SHADOW_CASTER` flag.
- [x] The same entity resolves to the material asset used by shadow
      specialization.
- [x] The same entity resolves to the render mesh asset used by shadow
      specialization.
- [x] A focused test or debug artifact proves missing specialization inputs no
      longer cause the pillar to be kept in `PendingShadowQueues`.

## Close Notes
2026-07-04: Closed with a focused `scrolling_fog` white-box test for the Bevy
`specialize_shadows` pre-work-item inputs. The pillar now resolves through
`RenderMaterialInstances`, `RenderMeshInstances`, `MaterialRuntimeRegistry`,
prepared StandardMaterial assets, `RenderMeshAssets`, and the shadow-caster
flag. The helper `render3d_shadow_specialization_queue_data` returns queue data
with a fresh `ViewPendingQueues` and does not add the pillar to pending.

The root cause for this slice was that the example only authored the legacy
erased `MeshMaterial3d` component, while Bevy's material owner maps to the typed
`MeshMaterial3d<StandardMaterial>` path. The example now provides the typed
StandardMaterial carrier required by `MaterialPlugin[StandardMaterial]`.
Because the current local visibility/extraction path still also depends on the
erased carrier, the broader source-parity cleanup is tracked separately in
ISS-236.
