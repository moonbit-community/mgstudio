# ISS-492: meshlet example renders an empty frame (both reference vintages broken)

## Metadata
- Type: bug
- Status: blocked
- Priority: 1
- Labels: meshlet, render, examples, visual-parity, external-blocker
- Assignee: unassigned

- External ref: wgpu-native (R64Uint + storage-texture atomic C API)

## Description

Human judgment on the ISS-481 chunk-2 capture: "meshlet is empty." The
fresh frame-90 capture of `examples/3d/meshlet` contains no meshlet
scene content — the white ground plane renders (regular Mesh3d path)
while all ten meshlet bunnies are absent, deterministically, with a
clean run log. Both reference vintages are broken states: black then,
empty-light now.

## Root cause (probe-proven 2026-08-06)

Staged probes (extract counters → raster/shade counters → feature
gates) walked the whole chain:

1. **Extract**: all 10 `MeshletMesh3d` entities are seen and the
   `bunny.meshlet_mesh` asset loads (`seen=10 ready=10 have_asset=10`),
   but only 5 extract (`matched=5`) — the extract gates on the legacy
   untyped `MeshMaterial3d` component, so the five colored bunnies
   (typed carrier) are skipped. This is the ISS-497 class inside the
   meshlet owner; Bevy resolves materials from the erased
   `RenderMaterialInstances` instead
   (`bevy_pbr/src/meshlet/instance_manager.rs::extract_meshlet_mesh_entities`).
2. **Raster**: `runtime=false pipelines_ready=false` every frame — the
   entire cull/visibility-buffer block is gated off by
   `meshlet_runtime_available()`, so the visibility buffer never fills.
   The shade pass still submits its draw (`draws=1`) against the empty
   buffer, producing zero fragments. Nothing crashes; the frame is
   silently plane-only.
3. **The gate is a deliberate, honest dependency blocker**:
   `@renderer.meshlet_missing_native_r64uint_storage_texture_api()` is
   hardcoded `true` because Bevy's visibility buffer is
   `texture_storage_2d<r64uint, atomic>` and the pinned wgpu-native C
   headers expose neither `R64Uint` nor storage-texture atomic access.
   wgpu_mbt's README records both under "Known Upstream Gaps" and
   deliberately refuses fake wrappers. The device also reports the
   TEXTURE_ATOMIC-class feature bits missing for the same upstream
   reason (`missing_feature_bits=70506451566592`,
   `subgroup_barrier_missing=false`). The hardware itself (Apple M3
   Max, Apple9 GPU) supports the features — pinned Bevy through Rust
   wgpu can render this example; the gap is exclusively the C ABI that
   MoonBit must use.

The silent-empty divergence vs Bevy: on a host lacking the features,
Bevy's `check_meshlet_features` logs an error and exits — it never
renders a deceptively fine-looking frame.

## External blocker record

- Dependency: wgpu-native (consumed through `Milky2018/wgpu_mbt`).
- Missing capability: `WGPUTextureFormat` `R64Uint` and
  `STORAGE_TEXTURE_ACCESS_ATOMIC` in the C header/conversion layer
  (wgpu_mbt README "Known Upstream Gaps").
- Bevy requirement: `texture_storage_2d<r64uint, atomic>` visibility
  buffer plus `TEXTURE_INT64_ATOMIC | TEXTURE_ATOMIC | SHADER_INT64 |
  SUBGROUP | DEPTH_CLIP_CONTROL | PUSH_CONSTANTS`
  (`MeshletPlugin::required_wgpu_features`).
- mgstudio owner: `pbr/meshlet` (runtime soft-disable in
  `render/renderer/mesh3d_runtime_api.mbt::meshlet_missing_native_r64uint_storage_texture_api`).
- Reproduction: run `examples/3d/meshlet`; the startup check logs
  "MeshletPlugin can't be used ..." and the frame shows only the ground
  plane.
- Verification expectation when unblocked: wgpu-native release exposes
  the format/access → wgpu_mbt wraps them → replace the hardcoded gate
  with a real device query → the raster block activates → frame-90
  capture human-judged against a pinned-Bevy spot (Bevy example needs
  the `meshlet` cargo feature).

## Fixed in this slice

Commit `3926ff987` (2026-08-06): ported Bevy's
`check_meshlet_features` as a render-startup system in the meshlet
plugin. Recorded divergence: Bevy exits (`std::process::exit(1)`)
because it cannot continue safely; mgstudio's runtime already
soft-disables all meshlet GPU work behind `meshlet_runtime_available()`
(the engineered blocker handling), so the port keeps the run alive and
adopts only the loud error report. The check mirrors Bevy's
`Res<RenderDevice>` dependency (headless test worlds skip it).
Verified: pbr/meshlet tests 14/14 with the `[ERROR]` line visible in
device-backed tests. Note: TERM-killed capture harness logs can still
miss the single buffered line (the known block-buffered-stdout loss
recorded since ISS-482); interactive and clean-exit runs show it.
