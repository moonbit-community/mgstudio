## Description
Even with the correct cubemap and shader, the skybox can diverge if
`Skybox::brightness`, exposure, rotation, or camera view/projection inputs are
encoded differently from Bevy.

## Design
Compare Bevy's `Skybox` component defaults, example usage, extraction, view
bind data, and shader uniform inputs against the mgstudio light/core-pipeline
fragments. This issue should prove the values used by the real
`volumetric_fog` camera rather than relying only on static code inspection.

## Acceptance Criteria
- [x] Bevy `Skybox` defaults and the `volumetric_fog` example brightness/image
      values are mapped to mgstudio symbols and runtime values.
- [x] Rotation, view direction, projection, and exposure inputs used by the
      skybox shader match Bevy semantics, or the precise divergence is fixed.
- [x] The close notes state whether brightness/view inputs remain a possible
      cause of the current `volumetric_fog` visual failure.

## Close Notes
Closed on 2026-07-05 by auditing Bevy `Skybox` component/defaults,
`volumetric_fog` example inputs, skybox extraction, and the view-uniform shader
input path against mgstudio.

Bevy source anchors:
- `bevy/crates/bevy_light/src/probe.rs::Skybox` defaults to `image=None`,
  `brightness=0.0`, and `rotation=Quat::IDENTITY`.
- `bevy/examples/3d/volumetric_fog.rs::setup` inserts `Skybox { image:
  Some(asset_server.load("environment_maps/pisa_specular_rgb9e5_zstd.ktx2")),
  brightness: 1000.0, ..default() }`, so rotation remains identity.
- `bevy/crates/bevy_core_pipeline/src/skybox/mod.rs::extract_skybox` writes
  `SkyboxUniforms.brightness = skybox.brightness * exposure`, using
  `Exposure::default().exposure()` when no camera `Exposure` component exists,
  and writes `Transform::from_rotation(skybox.rotation.inverse()).to_matrix()`.
- `bevy/crates/bevy_core_pipeline/src/skybox/skybox.wgsl` computes skybox ray
  direction from `view.view_from_clip`, `view.world_from_view`, and
  `uniforms.transform`.

Mgstudio implementation fragments:
- `mgstudio-engine/light/probe.mbt::Skybox` has the same defaults and plain
  fields.
- `mgstudio-engine/examples/3d/volumetric_fog/main.mbt::setup_camera` loads
  the same Pisa specular KTX2 asset and sets brightness to `1000.0F` through
  `Skybox::new`, preserving default identity rotation.
- `mgstudio-engine/core_pipeline/skybox/top.mbt::extract_skybox` uses the same
  optional exposure fallback and writes `SkyboxUniforms::from_skybox`, which
  multiplies brightness by exposure and converts inverse rotation to a 4x4
  transform.
- `mgstudio-engine/core_pipeline/skybox/top.mbt::skybox_bind_group_layout_descriptor`
  and `mgstudio-engine/render/renderer/gpu_skybox.mbt` bind the Bevy-shaped
  view uniform at binding 2. The WGSL source is byte-identical to Bevy's
  `skybox.wgsl` as recorded in ISS-351.

Evidence:
- Added `skybox: default exposure fallback scales brightness like Bevy extract`
  to prove the default `Exposure::Exposure().exposure()` path scales skybox
  brightness and identity rotation produces the identity transform.
- Extended `volumetric_fog: camera skybox and volumetric fog setup matches
  Bevy` to assert the real example camera uses the Pisa skybox image,
  brightness `1000.0F`, and identity rotation.
- ISS-351's descriptor test proves the shader view input is the same group 0
  binding 2 `ViewUniform` path used by Bevy.

Validation:
- `moon -C mgstudio-engine test core_pipeline/skybox --target native --release`
  passed `8/8`; duplicate `-lobjc` linker warnings were emitted.
- `moon -C mgstudio-engine test examples/3d/volumetric_fog --target native --release --filter 'volumetric_fog: camera skybox and volumetric fog setup matches Bevy'`
  passed `1/1`; duplicate `-lobjc` and `-lz` linker warnings were emitted.

Conclusion: brightness, default exposure fallback, identity rotation, and
view/projection binding are classified as complete for this audit and are not
remaining candidate root causes for the current `examples/3d/volumetric_fog`
near-grey visual failure.
