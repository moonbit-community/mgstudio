# ISS-488: Lightmap contribution lost — lightmaps example renders black

## Description

`examples/3d/lightmaps` (Cornell Box lit exclusively by baked lightmaps,
ambient zero) renders BLACK except the emissive ceiling quad and the
clear-color margins: the lightmap contribution never reaches the shaded
result. Wall samples that should be the red/green/white lightmapped
surfaces read ~(1,0,0)/(1,1,1) (dither noise around zero) where both the
old committed reference and pinned Bevy show (108,3,2)-class walls.

NOT caused by the ISS-483 tonemapping slice: a bisect capture at
`908dad3a3` (the commit before the tonemapping work) shows the identical
black box. The old committed reference is nearly Bevy-perfect
(mean_abs_rgb 2.69 vs a fresh pinned-Bevy frame-90 capture), so the
feature worked when that reference was captured. Same silent-breakage
family as ISS-482: the run log is clean, nothing crashes, the
contribution is just zero.

## Root causes (probe-proven 2026-08-06)

Staged probes (example system → extract payload → RenderLightmaps
inserts → specialization lookups → prepare marking) proved a two-layer
failure. The KTX2 path was exonerated first (vkFormat 122 =
B10G11R11_UFLOAT maps correctly), and the run log stayed empty under
ISS-482's pipeline-error logging, ruling out the pipeline-creation
class.

1. **The example queried a dead component** (breaking commit
   `05a64d8d5` "Port scene glTF materials to typed carrier"): the glTF
   scene spawner writes the typed `MeshMaterial3dTyped[StandardMaterial]`
   carrier, but the example's `add_lightmaps_to_meshes` query read the
   legacy untyped `@pbr.MeshMaterial3d`, which nothing attaches to
   glTF-spawned entities. The query matched zero entities all run
   (probe: zero `sys` lines; component probe: `GltfMeshName` present,
   `mat=false` on every mesh entity every frame), so no `Lightmap`
   component was ever inserted. Pinned Bevy's example queries the typed
   component (`&MeshMaterial3d<StandardMaterial>`,
   `examples/3d/lightmaps.rs:67`). The wider untyped-reader debt is
   filed as ISS-497.
2. **The `RenderLightmaps` lifecycle was inverted vs Bevy** — with the
   example fixed, the box STILL rendered black: the table was populated
   at DRAW time (`render3d_resolve_mesh_lightmap_draw_fields` allocated
   slots) and cleared every frame by the main pass, while pipeline
   specialization reads it earlier in the frame. The one-frame trace
   shows the race exactly: Update inserts `Lightmap` + mutates the
   material assets → prepare marks all six entities for specialization
   (the asset-changed edge works) → specialization re-runs the same
   frame and reads `mapsize=0` → draw then fills the table (1..5) → the
   main pass clears it again. The single specialization window always
   lost, so the `LIGHTMAP` define never activated. Bevy populates the
   table in `ExtractSchedule` (`extract_lightmaps`, change-driven,
   persistent resource) before anything reads it.

## Fix

Commit `c7d6611d0` (2026-08-06):

- `pbr/lightmap/top.mbt`: ported Bevy's `extract_lightmaps`
  (`bevy_pbr/src/lightmap/mod.rs`) as `extract_lightmaps_system`,
  registered by the lightmap plugin in the render extract stage:
  entities with changed `ViewVisibility` or `Lightmap` allocate a slab
  slot when visible (insert is idempotent, matching Bevy's
  `contains_key` skip), removed `Lightmap` components free theirs, and
  the table persists across frames. Change detection uses a
  `last_source_change_tick` cursor on `RenderLightmaps`, following the
  `RenderMaterialInstances` idiom.
- `pbr/render_startup.mbt`: ported `init_render_lightmaps` — the
  bindless capability is decided once at render startup so slab
  capacities are stable for the run (it lives in pbr because the
  capability check needs the pbr texture-binding constants).
- `pbr/render_execute_camera_main_pass.mbt`: deleted the per-frame
  `set_bindless_supported` + `clear()` block.
- `pbr/render_execute_draw_material.mbt`:
  `render3d_resolve_mesh_lightmap_draw_fields` is now a pure read of
  `RenderLightmaps` (slab/slot/uv-rect from the table), so the draw
  payload and the specialized pipeline stay coherent; an entity absent
  from the table draws without a lightmap, matching its non-`LIGHTMAP`
  pipeline.
- `examples/3d/lightmaps/main.mbt`: query ported to the typed carrier
  exactly as Bevy's example, and the exposure helper takes the typed
  handle directly.
- Intentional exclusion, recorded: Bevy's `pending_lightmaps` /
  `AllocatedLightmap` GpuImage staging is not ported — mgstudio's slab
  stores texture ids that the host-gpu backend resolves at bind time,
  so there is no GpuImage binding-array staging step to mirror.
