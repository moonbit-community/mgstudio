# ISS-482: Anisotropy barn-lamp meshes silently vanish from the render

## Metadata
- Type: bug
- Status: open
- Priority: 1
- Labels: pbr, materials, anisotropy, gltf, examples, visual-parity, regression
- Assignee: unassigned
- Created: 2026-08-04
- Updated: 2026-08-04
- External ref: none

## Description

`examples/3d/anisotropy` renders only the lamp bulb at frame 90; the rest of
the AnisotropyBarnLamp glTF — wall mount plate, arm, joint, and shade — is
absent from the image. The run log is empty: no fatal, validation,
unsupported-feature, or binding-mismatch message. The meshes disappear
silently.

The missing meshes are exactly the ones whose glTF materials carry the
KHR_materials_anisotropy texture route (the feature-variant StandardMaterial
path); the bulb that still renders uses a plain material. The example still
wires the feature selection ISS-164 added
(`examples/3d/anisotropy/main.mbt:522`:
`PbrPlugin::PbrPlugin().with_standard_material_texture_features(
StandardMaterialTextureFeatureSet(pbr_anisotropy_texture=true))`), so the
regression is engine-side, not example-side.

Found during the ISS-481 reference regeneration sweep; the human reviewer
flagged the capture ("looks very bad") before any install. The old reference
stays in place and the example is excluded from ISS-481 until this is fixed.

## Source trail (suspects, not proven root cause)

- The material-system refactors in the window, e.g. `79a8e5464 Retire erased
  StandardMaterial authoring` and `a1d351e2d Refactor material draw data
  tracking` — feature-variant bind-group/draw-data tracking is exactly the
  surface whose loss would hide only the variant-material meshes.
- The ISS-019 retained-phase slices were A/B byte-verified, but only on
  examples without feature-variant materials (ssao, motion_blur,
  deferred_rendering); they have not been ruled out for the variant path.
- The silent-skip is itself a defect class: a mesh dropped for a missing or
  unbuildable material variant should surface a diagnostic, not vanish.

## Design

Bisect the 2026-07-01..2026-08-04 window with the frame-90 capture as the
probe (cheap per step once built; do not run while other captures share the
build directory), or instrument the variant-material draw path to log skipped
meshes and read the reason directly. Fix at the root per repo policy — no
draw-path workaround.

## Root cause for the decal member (proven 2026-08-05)

Probe chain on `examples/3d/decal` (wgpu uncaptured-error stderr via the
existing `MGSTUDIO_WGPU_UNCAPTURED_ERROR_STDERR=1` hook, plus staged
`[DEBUG-482]` printlns under a pty — block-buffered stdout dies with the
SIGABRT otherwise):

1. The submit crash is secondary. The primary failure is at CREATE time:
   `wgpuDeviceCreateRenderPipeline`: "Shader global ResourceBinding
   { group: 3, binding: 0 } is not available in the pipeline layout" —
   group 3 binding 0 is the StandardMaterial uniform
   (`pbr_bindings.wgsl:45`, `MATERIAL_BIND_GROUP_INDEX = 3`).
2. pty ordering names the create site: the SHADOW pipeline with
   `material_path=true` (`mesh3d_pipeline_build.mbt` shadow builder),
   which composes the material-sampling `pbr/render/pbr_prepass.wgsl`
   fragment but takes its material group from
   `mesh3d_material_pipeline_layout_get_or_create(id, descriptor)` where
   the id is a DEPTH-ONLY prepass descriptor (`layout[3]` empty) — the
   renderer pairs a material-referencing fragment with a material-less
   layout.
3. WHY the draw carries a prepass id at all: the decal entity never
   specializes — `[DEBUG-482] specialize-skip entity=4
   reason=no_resolved_material` every frame, while all 101
   StandardMaterial entities specialize fine. Its resolved-material slot
   stays `Pending` forever because `prepare_material_assets_system[M]`
   NEVER RUNS for M=ForwardDecalMaterial.
4. THE ROOT: `ForwardDecalPlugin::build` (`pbr/decal/forward.mbt`)
   initializes `Assets<ForwardDecalMaterial>`, the decal mesh, and the
   component hook — but never installs
   `MaterialPlugin[ForwardDecalMaterial]`. Bevy's `ForwardDecalPlugin`
   adds `MaterialPlugin::<ForwardDecalMaterial<StandardMaterial>>`
   (`bevy_pbr/src/decal/forward.rs:43`). Deeper: NOTHING in the engine
   implements `StandardMaterialExtension`, so the entire
   `ExtendedMaterial[StandardMaterial, E] : Material` machinery
   (`extended_material.mbt:493+`, complete and Bevy-faithful, including
   `ForwardDecalMaterialExtension`'s MaterialExtension impl with alpha
   Blend / shadows-off / the depth-Always+FORWARD_DECAL specialize) has
   ZERO live instantiations. Extension materials instead route through
   the untyped `material_family` shim
   (`forward_decal_mesh_material3d` -> `MeshMaterial3d` with family),
   which no extraction system consumes -> Pending -> silent vanish.
5. The anisotropy member is likely the same family but is
   StandardMaterial-based (feature textures, not an extension) — it
   needs its own probe run after the decal fix lands; do not assume the
   same mechanism.

Fix (Bevy-shaped, mirroring `bevy_pbr/src/decal/forward.rs`):

- Implement `StandardMaterialExtension for ForwardDecalMaterialExtension`
  (static asset/material keys registrations + shader-ref Nones +
  enable_shadows_ref false + the existing `forward_decal_specialize` as
  `specialize_ref`), making
  `ExtendedMaterial[StandardMaterial, ForwardDecalMaterialExtension]` a
  real `Material`.
- Define the pbr-level `ForwardDecalMaterial` as that ExtendedMaterial
  type (Bevy's alias shape), register
  `MaterialPlugin[ForwardDecalMaterial]` in `pbr_plugin` (the package
  split keeps the generic plugin in `pbr`, so the registration lives
  next to `ForwardDecalPlugin` in `pbr/lib.mbt`), and route the typed
  `MeshMaterial3dTyped` component through `forward_decal_mesh_material3d`.
- Retire the `@decal.ForwardDecalMaterial` plain struct + family shim
  once the typed path draws (delete-legacy rule), including the
  extension uniform (binding 200) flowing through the extension
  bind-group metadata rather than the ad-hoc draw param.

## Fix landed for the decal member (2026-08-05)

Implemented exactly the recorded plan:

1. `StandardMaterialExtension for ForwardDecalMaterialExtension`
   (`pbr/extended_material.mbt`): static asset/material key registrations
   (`register_material_keys("mgstudio_pbr::ForwardDecalMaterial")`),
   default shader refs, `enable_shadows_ref = false` (Bevy:
   `ForwardDecalMaterialExt::enable_shadows() -> false`), and the
   existing `forward_decal_specialize` as `specialize_ref`. The
   extension now also declares its binding-200 uniform through
   `bind_group_layout_entries`/`bind_group_bindings` (Bevy's
   `#[uniform(200, ForwardDecalMaterialExtUniform)]`), superseding the
   ad-hoc draw-param path (guarded in
   `render/renderer/mesh3d_bind_groups.mbt` so binding 200 has a single
   source; the leftover param path dies with the family shim).
2. `pbr/mesh.mbt`: `ForwardDecalMaterial` is now the Bevy-shaped alias
   `ExtendedMaterial[StandardMaterial, ForwardDecalMaterialExtension]`
   with a `forward_decal_material(base, ext)` constructor, and
   `forward_decal_mesh_material3d` returns the TYPED
   `MeshMaterial3dTyped[ForwardDecalMaterial]` component.
3. `pbr/lib.mbt`: `MaterialPlugin[ForwardDecalMaterial]` registered next
   to `ForwardDecalPlugin` (Bevy adds it inside the decal plugin; the
   package split keeps the generic plugin in `pbr`).
4. `examples/3d/decal` uses the typed constructor.

Verification: the decal capture no longer crashes — frame-90 EXIT 0 with
an EMPTY run log (was: wgpuQueueSubmit abort every run); the scene
renders. `moon check` clean, fmt/info clean, fog tests pass; ssao and
motion_blur gates BYTE-CANON (`4eaf5a6585dc926b...`,
`1769770807e43c9f...`). The atmospheric_fog gate flaked fog-off on one
run — bisect proves the slice merely perturbs startup timing and the
dropout is the pre-existing fog-binding fragility, now tracked as
ISS-494 (probed runs with this slice render fog at the exact ISS-483
parity values).

NOT fixed by this slice: the anisotropy member. Its capture is now
clean-logged but the barn-lamp meshes are still absent (background at
all sampled interior points; only the bulb renders) — StandardMaterial
feature-texture routing, a different mechanism than the extension
family. Needs its own staged probe run (glTF material handler ->
feature-set routing -> typed instance extraction).

## Root causes for the anisotropy member (proven 2026-08-05)

The staged probe run walked the whole chain (glTF primitive spawn ->
mesh extraction -> material resolve -> specialize -> queue -> backend
draw) and found the meshes were NEVER dropped on the CPU side: all 3
glTF primitives spawn with typed materials, extract, specialize, and
queue every frame. The vanish happens at backend draw: the "Lamp Metal"
item carries `material_pipeline_id=0` and the backend registry has no
pipeline 0, so `draw_mesh3d_main_pass` silently returns. Pipeline 0's
creation had failed inside the pipeline-cache materializer with a
SWALLOWED error:

```
wgpu: failed to resolve shader import:
pbr_bindings::clearcoat_normal_texture in
pbr_input_from_standard_material
```

Two stacked defects, both with named breaking commits:

1. UNGATED KEY BIT (`50aca3a4a` "pbr: expand bevy-aligned
   material/medium/transmission surfaces"):
   `standard_material_key_from_material` set
   `STANDARD_MATERIAL_KEY_CLEARCOAT_NORMAL_MAP` from the material alone,
   while Bevy gates that insert behind
   `#[cfg(feature = "pbr_multi_layer_material_textures")]`
   (`bevy_pbr/src/pbr_material.rs`). The barn lamp's "Lamp Metal"
   carries `KHR_materials_clearcoat` WITH `clearcoatNormalTexture`, and
   Bevy's anisotropy example compiles WITHOUT that cargo feature — so
   Bevy drops the clearcoat textures wholesale while mgstudio emitted
   the shader define against a bindings module that (correctly,
   feature-gated) omitted the binding -> unresolvable import ->
   pipeline error -> silent skip of every draw using it.
2. KTX2 vkFormat TABLE ERROR (`afac35f0a` "Fix PBR internal LUT
   bindings"): `KTX2_VK_FORMAT_R8_UNORM` was defined as 23, but
   VK_FORMAT_R8_UNORM is 9 — 23 is VK_FORMAT_R8G8B8_UNORM. Every RGB8
   KTX2 (the barn lamp's normal/ORM/anisotropy textures AND the
   engine's own `pbr/bluenoise/stbn.ktx2`) "decoded" as R8 by clipping
   the first W*H bytes of the interleaved RGB stream — channel garbage
   certified by a wbtest expecting R8. Bevy transcodes RGB8 KTX2 levels
   to RGBA8 (`bevy_image/src/ktx2.rs`, `TranscodeFormat::Rgb8`).

## Fix landed for the anisotropy member (2026-08-05)

1. `standard_material_key_from_material` now takes the
   `StandardMaterialTextureFeatureSet` and gates CLEARCOAT_NORMAL_MAP on
   `pbr_multi_layer_material_textures`, mirroring Bevy's cfg. The
   runtime feature set is this port's equivalent of Bevy's cargo
   features, so the `Material` trait's `material_key`/`bind_group_data`
   methods now receive the `MaterialBindGroupContext` (the trait already
   passed it to `bind_group_layout_descriptor`); all impls and the
   custom-material examples updated. Regression test added: the key bit
   stays clear with the feature off even when the material carries the
   texture.
2. The KTX2 table now maps 9 -> R8_UNORM and 23/29 ->
   RGB8(-SRGB) with a Bevy-shaped per-level RGB8->RGBA8 transcode
   (alpha=255) in both the 2d and 3d decode paths. The stbn wbtest
   expectation corrected to RGBA8 (128x128x32x4 bytes).
3. DIAGNOSTIC (acceptance criterion 3): the pipeline-cache materializer
   no longer swallows creation failures — non-retryable errors log
   `failed to create render/compute pipeline N: ...` via
   `@app.log_error`, mirroring Bevy's `PipelineCache` error logging.
   The whole silent-vanish class is now loud.
