# ISS-482: Anisotropy barn-lamp meshes silently vanish from the render

## Metadata
- Type: bug
- Status: open
- Priority: 1
- Labels: pbr, materials, anisotropy, gltf, examples, visual-parity, regression
- Assignee: unassigned
- Created: 2026-08-04
- Updated: 2026-08-04
- External ref: none

## Description

`examples/3d/anisotropy` renders only the lamp bulb at frame 90; the rest of
the AnisotropyBarnLamp glTF — wall mount plate, arm, joint, and shade — is
absent from the image. The run log is empty: no fatal, validation,
unsupported-feature, or binding-mismatch message. The meshes disappear
silently.

The missing meshes are exactly the ones whose glTF materials carry the
KHR_materials_anisotropy texture route (the feature-variant StandardMaterial
path); the bulb that still renders uses a plain material. The example still
wires the feature selection ISS-164 added
(`examples/3d/anisotropy/main.mbt:522`:
`PbrPlugin::PbrPlugin().with_standard_material_texture_features(
StandardMaterialTextureFeatureSet(pbr_anisotropy_texture=true))`), so the
regression is engine-side, not example-side.

Found during the ISS-481 reference regeneration sweep; the human reviewer
flagged the capture ("looks very bad") before any install. The old reference
stays in place and the example is excluded from ISS-481 until this is fixed.

## Evidence

  Lamp scene with the anisotropy help text visible".
- Checked-in reference (2026-06-19, `7c9c59bf8 Restore anisotropy source

- The regression window is therefore 2026-07-01 .. 2026-08-04.

## Source trail (suspects, not proven root cause)

- The material-system refactors in the window, e.g. `79a8e5464 Retire erased
  StandardMaterial authoring` and `a1d351e2d Refactor material draw data
  tracking` — feature-variant bind-group/draw-data tracking is exactly the
  surface whose loss would hide only the variant-material meshes.
- The ISS-019 retained-phase slices were A/B byte-verified, but only on
  examples without feature-variant materials (ssao, motion_blur,
  deferred_rendering); they have not been ruled out for the variant path.
- The silent-skip is itself a defect class: a mesh dropped for a missing or
  unbuildable material variant should surface a diagnostic, not vanish.

## Design

Bisect the 2026-07-01..2026-08-04 window with the frame-90 capture as the
probe (cheap per step once built; do not run while other captures share the
build directory), or instrument the variant-material draw path to log skipped
meshes and read the reason directly. Fix at the root per repo policy — no
draw-path workaround.

## Root cause for the decal member (proven 2026-08-05)

Probe chain on `examples/3d/decal` (wgpu uncaptured-error stderr via the
existing `MGSTUDIO_WGPU_UNCAPTURED_ERROR_STDERR=1` hook, plus staged
`[DEBUG-482]` printlns under a pty — block-buffered stdout dies with the
SIGABRT otherwise):

1. The submit crash is secondary. The primary failure is at CREATE time:
   `wgpuDeviceCreateRenderPipeline`: "Shader global ResourceBinding
   { group: 3, binding: 0 } is not available in the pipeline layout" —
   group 3 binding 0 is the StandardMaterial uniform
   (`pbr_bindings.wgsl:45`, `MATERIAL_BIND_GROUP_INDEX = 3`).
2. pty ordering names the create site: the SHADOW pipeline with
   `material_path=true` (`mesh3d_pipeline_build.mbt` shadow builder),
   which composes the material-sampling `pbr/render/pbr_prepass.wgsl`
   fragment but takes its material group from
   `mesh3d_material_pipeline_layout_get_or_create(id, descriptor)` where
   the id is a DEPTH-ONLY prepass descriptor (`layout[3]` empty) — the
   renderer pairs a material-referencing fragment with a material-less
   layout.
3. WHY the draw carries a prepass id at all: the decal entity never
   specializes — `[DEBUG-482] specialize-skip entity=4
   reason=no_resolved_material` every frame, while all 101
   StandardMaterial entities specialize fine. Its resolved-material slot
   stays `Pending` forever because `prepare_material_assets_system[M]`
   NEVER RUNS for M=ForwardDecalMaterial.
4. THE ROOT: `ForwardDecalPlugin::build` (`pbr/decal/forward.mbt`)
   initializes `Assets<ForwardDecalMaterial>`, the decal mesh, and the
   component hook — but never installs
   `MaterialPlugin[ForwardDecalMaterial]`. Bevy's `ForwardDecalPlugin`
   adds `MaterialPlugin::<ForwardDecalMaterial<StandardMaterial>>`
   (`bevy_pbr/src/decal/forward.rs:43`). Deeper: NOTHING in the engine
   implements `StandardMaterialExtension`, so the entire
   `ExtendedMaterial[StandardMaterial, E] : Material` machinery
   (`extended_material.mbt:493+`, complete and Bevy-faithful, including
   `ForwardDecalMaterialExtension`'s MaterialExtension impl with alpha
   Blend / shadows-off / the depth-Always+FORWARD_DECAL specialize) has
   ZERO live instantiations. Extension materials instead route through
   the untyped `material_family` shim
   (`forward_decal_mesh_material3d` -> `MeshMaterial3d` with family),
   which no extraction system consumes -> Pending -> silent vanish.
5. The anisotropy member is likely the same family but is
   StandardMaterial-based (feature textures, not an extension) — it
   needs its own probe run after the decal fix lands; do not assume the
   same mechanism.

Fix (Bevy-shaped, mirroring `bevy_pbr/src/decal/forward.rs`):

- Implement `StandardMaterialExtension for ForwardDecalMaterialExtension`
  (static asset/material keys registrations + shader-ref Nones +
  enable_shadows_ref false + the existing `forward_decal_specialize` as
  `specialize_ref`), making
  `ExtendedMaterial[StandardMaterial, ForwardDecalMaterialExtension]` a
  real `Material`.
- Define the pbr-level `ForwardDecalMaterial` as that ExtendedMaterial
  type (Bevy's alias shape), register
  `MaterialPlugin[ForwardDecalMaterial]` in `pbr_plugin` (the package
  split keeps the generic plugin in `pbr`, so the registration lives
  next to `ForwardDecalPlugin` in `pbr/lib.mbt`), and route the typed
  `MeshMaterial3dTyped` component through `forward_decal_mesh_material3d`.
- Retire the `@decal.ForwardDecalMaterial` plain struct + family shim
  once the typed path draws (delete-legacy rule), including the
  extension uniform (binding 200) flowing through the extension
  bind-group metadata rather than the ad-hoc draw param.
