## Description

`QueryData` currently combines access declaration, archetype matching, fetch
planning, table-row fetching, sparse fetching, and the returned row item in one
`Self` type. Prototype the minimum separation needed for persistent query state
and typed table fetch state.

## Acceptance Criteria

- [x] The design explicitly maps query specification, state, table fetch, and
      item responsibilities to the pinned Bevy query owner.
- [x] The prototype preserves tuple, optional, `Has`, sparse-set, and change
      filter semantics required by the selected test surface.
- [x] One focused ECS query test runs at a time with
      `MOONBIT_NEW_NATIVE=1`.
- [x] `examples/stress_tests/many_components` is the only runtime example gate.
- [x] The retained/rejected decision follows the `ISS-444` experiment protocol.

## Notes

- 2026-07-15: Started after retaining `ISS-446`. The first prototype will
  isolate the persistent `WorldQuery::State` responsibility by reusing the
  existing fetch plan across system-param runs. It will not bind typed columns
  or change row-item materialization; those remain `ISS-448` and `ISS-449`.
- 2026-07-15: Before changing code, the existing 20,000-row four-component
  benchmark measured `7.73 ms` through `QueryCache` and `7.28 ms` through
  `QueryState`, indicating that the already-persistent fetch plan may account
  for a measurable part of the boundary but not yet isolating it from the
  different matching-state implementation.

## Close Notes

Rejected and reverted on 2026-07-15 because persistent fetch-plan state did not
improve either the isolated query kernel or the target runtime systems.

- Bevy maps the responsibilities as follows: the query data/filter types are
  the specification; `QueryState::{fetch_state, filter_state}` is persistent;
  `WorldQuery::Fetch` is rebound by `set_table`/`set_archetype`; and
  `QueryData::Item` is the returned row item.
- The prototype added a typed `QueryFetchState[D]`, initialized it in each
  system parameter, reused its `QueryDataFetchPlan` across runs, and left
  tuple, optional, `Has`, sparse-set, change-filter, table-fetch, and row-item
  code unchanged. A repeated-query ECS test and the existing repeated mutable
  query-system-param test passed separately.
- The isolated 20,000-row four-component query benchmark moved from `7.73 ms`
  to `7.85 ms`, a 1.55% regression. This disproves the earlier inference that
  the `7.28 ms` `QueryState` result was primarily caused by fetch-plan reuse;
  the remaining difference belongs to the matching/iteration path.
- Before: `/tmp/mgstudio_iss447_many_components_before_20260715/frametime_breakdown.md`
  reported `22.224 ms/frame`. The three example Update systems cost
  `7.369 ms`, `8.991 ms`, and `0.845 ms`, or `17.205 ms` combined.
- After: `/tmp/mgstudio_iss447_many_components_after_20260715/frametime_breakdown.md`
  reported `22.561 ms/frame`. The same systems cost `7.386 ms`, `9.012 ms`,
  and `0.863 ms`, or `17.261 ms` combined. Target cost regressed 0.33% and
  whole-frame time regressed 1.52%.
- Native ECS and app checks completed with no errors. App warning 83 output is
  pre-existing and tracked by `ISS-443`.
- No production API, test, benchmark, or generated-interface change from the
  prototype remains.
