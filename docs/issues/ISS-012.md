## Description
The current render/PBR/mesh/light stack has broad file, shader, resource, and
example coverage, but it is not complete under the strict Bevy source-level
parity standard. Visual plausibility is not sufficient: each source owner,
struct, function, schedule edge, render-world resource, phase command, and
example data flow must be classified as complete, facade, partial, or blocked.

Do not summarize the current state as a completion percentage. PBR, mesh, and
light are in a late-stage but still-open migration state: most visible examples
and many source fragments exist, while the remaining owner-boundary work is
small in file count but high in risk. The remaining work includes source of
truth migration, phase command consumption, runtime queueing, and exact
example/source-shape parity, so it cannot be treated as "the last few percent"
or as closure evidence.

Current area status for planning and triage:

| Area | Tracker Status | Tracker Meaning |
| --- | --- | --- |
| PBR | late-stage open | Material, light-probe, shader-source, and standard-material fragments exist, but source-level parity is still blocked by material owner routing, phase command consumption, postprocess/prepass/deferred integration, and specialized example source-shape gaps. |
| Mesh | late-stage open, lower confidence | `RenderMeshInstances`, mesh flags, visibility ranges, and render-asset consumers have real owner work, but the old extracted-mesh/collect path still owns too much preparation state and meshlet visibility-buffer parity is still not exact. |
| Light/shadow | late-stage open | Directional light, cascade, shadow, and many example paths are close, but volumetric fog, atmosphere/scattering, selected shadow-pass consumers, and view-resource ownership still keep the area open. |

Only count a package, example, struct, or function as complete when its Bevy
source anchor is classified symbol-by-symbol, every local approximation has
either been removed or explicitly downgraded to incomplete, and the relevant
runtime path is verified by tests or visual evidence.

Current area interpretation:

- PBR is close on material, light-probe, shader-source, and many standard
  material paths, but still incomplete wherever pass ownership, phase command
  execution, postprocess/prepass/deferred integration, or specialized example
  source shape is not Bevy-shaped.
- Mesh has real progress in `RenderMeshInstances`, mesh flags, visibility
  ranges, and render-asset consumers, but remains below PBR/light because the
  old extracted-mesh/collect path still owns too much preparation state and the
  meshlet visibility-buffer path is not exact.
- Light/shadow has the highest source-owner coverage, but it is not complete
  while volumetric fog, atmosphere/scattering, shadow-pass consumers, light
  examples, and some view-resource ownership remain open or blocked.

Do not translate the late-stage status into "PBR is done", "mesh is done", or
"light is done". The only valid closure signal is child-issue closure or a
precise blocker/defer record for every remaining source anchor. If a future
status report needs a number, label it explicitly as a rough planning estimate,
not as parity completion.

The current most important local source-owner gap is `ISS-155`: the Bevy PBR
material owner and render mesh owner are partially ported, but standard
material preparation, specialization, queueing, and the remaining old
`ExtractedMesh3d` adapter still prevent the PBR/mesh boundary from being called
complete. Treat `ISS-155` as local migration work, not as an upstream blocker.

Older strict-roadmap scores such as `pbr=58%`, `pbr/render=71%`,
`pbr/prepass=59%`, and `pbr/meshlet=50%` were useful early baselines, but they
are no longer the right description after the later material, light probe,
shadow, mesh preparation, example, and shader-source work. They must not be
used as the current migration status.

This epic tracks the remaining high-level render/PBR parity work found by
comparing `mgstudio-engine/render`, `mgstudio-engine/pbr`,
`mgstudio-engine/mesh`, and `mgstudio-engine/light` against the current local
`./bevy` baseline.

## Design
Treat Bevy source ownership as the acceptance surface. Directory names, file
presence, WGSL presence, and plausible screenshots are not enough: plugin build
order, render sub-app lifecycle, render graph scheduling, resource
initialization, pass phase ownership, command execution, visual output, and
performance behavior must converge.

The largest remaining local gaps are PBR phase-command consumption, renderer
pass ownership, render-app system ordering, mesh preparation owner cleanup,
source-shaped visual gates, custom shader/custom material paths, skybox/OIT
paths, SSAO/volumetric fog/atmosphere ownership, and full GPU-preprocessing
runtime parity. These are local migration tasks unless a child issue names a
specific missing API or language feature.

The current explicit blocker classes are narrow: exact meshlet
visibility-buffer behavior still depends on WebGPU/C-ABI unsupported
`R64Uint`/atomic-storage-texture behavior or an approved algorithmic
replacement; selected GPU readback/callback and texture-format feature-query
surfaces are tracked separately; and a few source shapes depend on MoonBit
language features such as associated builder output shape, parallel mutable ECS
iteration, or exact curve/chromatic-phase APIs. Do not promote ordinary local
shortcuts, missing example code, or incomplete render pass wiring to blocker
status.

## Acceptance Criteria
- [ ] `render`, `render/renderer`, `pbr`, `pbr/render`, `pbr/prepass`, `mesh`, `light`, and unblocked `pbr/meshlet` items all reach at least `95%` in `docs/ROADMAP_CHECKLIST.md`.
- [ ] Every child issue is closed, deferred with an explicit blocker, or replaced by a more specific issue.
- [ ] Representative 2D, 3D, PBR, prepass/deferred, shadow, transmission, and meshlet examples have current visual parity evidence or explicit blockers.
- [ ] `docs/ROADMAP_CHECKLIST.md` no longer describes renderer ownership, render-graph integration, pass layout, PBR runtime consumption, or visual parity as major gaps without an open child issue.
