## Description

Raw tables own entities and change metadata while `ComponentKey[T]` closures own
typed values. Structural insert, move, swap-remove, take, despawn, rollback, and
world close therefore coordinate two storage authorities. Test a table-owned
transaction boundary that moves payload and metadata together while preserving
typed MoonBit storage.

## Acceptance Criteria

- [ ] The design is mapped source-by-source to pinned-Bevy table move and
      column ownership semantics.
- [ ] Insert, replace, move, take, remove, despawn, rollback, and close preserve
      exactly-once finalization.
- [ ] The retained path does not expose an intermediate raw/typed mismatch.
- [ ] One focused ECS structural test runs at a time with
      `MOONBIT_NEW_NATIVE=1`.
- [ ] `examples/3d/despawn3` is the only runtime example gate.
- [ ] The retained/rejected decision follows the `ISS-444` experiment protocol.

## Notes

- 2026-07-16: The pinned Bevy baseline owns component payload, added/changed
  ticks, and changed caller metadata in one `Column`. During
  `Tables::move_row`, `Column::initialize_from_unchecked` swap-removes all four
  source buffers and initializes the destination row in one operation
  (`bevy/crates/bevy_ecs/src/storage/table/mod.rs` and
  `storage/table/column.rs`). Removed source-only columns use the same
  `swap_remove_unchecked::<DROP>` boundary.
- 2026-07-16: The isolated MoonBit variable is one combined typed payload
  transfer for shared columns. Today target append calls
  `ComponentOps::move_table_row`, then source removal separately calls
  `ComponentOps::swap_remove_table_row`, causing two typed per-world store
  lookups. The prototype will first finish every fallible raw target-column
  preparation, then transfer and source-swap-remove a shared typed payload in
  one component operation. Source raw metadata removal remains table-owned;
  source-only typed values still use the existing removal path.
- 2026-07-16: The pre-change `insert velocity migration x5000` benchmark was
  `25.65 ms` and `28.17 ms` (mean `26.91 ms`). Two instrumented
  `examples/3d/despawn3` runs crossed the first five-second despawn, printed
  one removal, and ended at `1614.70 ms` and `1615.72 ms` frame time (mean
  `1615.21 ms`). The instrumentation is measurement-only and is not committed.
- 2026-07-16: The example gate uses
  `MGSTUDIO_RENDER3D_DISABLE_GPU_PREPROCESS=1`, matching the repository's
  native capture default. Without it, the unchanged baseline aborts on frame
  three with `Missing MeshInputUniform for queued pbr GPU mesh instance`.
