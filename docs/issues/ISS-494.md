## Description

The ISS-483 fourth fix (resolving the per-camera fog binding through
`SortedCameras` by id) removed one source of whole-frame fog dropout, but
a residual startup-timing fragility remains somewhere in the fog chain.
Registering `MaterialPlugin[ForwardDecalMaterial]` (ISS-482's fix — new
systems + ecs key registrations, no fog-related code) was enough to
reproduce a full-frame fog-off atmospheric_fog capture again:

- Capture-script run with the ISS-482 slice: hash `8ed1ed8d7469748a...`,
  sky flat (129,129,129), terrain green-but-unfogged — everything except
  DistanceFog correct (tonemap applied, materials fine).
- Repeat runs with probes: fog EXACT at the ISS-483 parity values
  ((80,114,167) sky, (226,228,229) glow), including a frame-90 run —
  intermittent, roughly 1-in-4 on the day.
- Probes in the good runs show every checked link healthy:
  `render3d_prepare_camera_fog_uniforms` sees the render-world camera
  with the DistanceFog component (`has_fog=true` every frame), and the
  pass config computes `fog_enabled=true` every frame. The failing link
  therefore sits between those probes and the uploaded uniform (the
  binding/offset path or the pass-kind consumption) OR the probes'
  observed runs simply never hit the failure; a failing-run probe capture
  is still missing.

Standard frame-90 capture of `examples/3d/atmospheric_fog`, repeated;

## Root cause (proven 2026-08-05, failing runs caught with probes live)

Three failing runs were caught (1-in-4-ish rate confirmed: 3 of 11
valid runs) with a staged probe set across the whole chain. The
failing-run signature (artifacts `run16.log`, `run17.log`; round-1
evidence `run5.log`):

- MAIN world: camera entity `3:1` — payload collect `fog=true`, pass
  config `fog_enabled=true`, view-key `fogbit=true`, pipeline
  `specialize fogbit=true`. All healthy.
- RENDER world: camera entity `4:1` — DistanceFog extracted every
  frame, `render3d_prepare_fog_system` resolves it (`alive=true
  fog=true`) and writes `ViewFogUniformOffset` onto `4:1`. Healthy.
- The main pass then called `render3d_prepare_camera_fog_binding` with
  the MAIN-world entity `3:1`; the resolver id-scanned `SortedCameras`
  (which holds RENDER-world entities, here `4:1`) -> no id match ->
  `PREPARED-MISS` -> `GpuFog::off()` uploaded EVERY frame.

In good runs the two worlds coincidentally allocate the same index for
the camera (both `4`), so the id-only scan accidentally matched. Any
startup-timing perturbation that shifts entity allocation order in
either world (the ISS-482 plugin registration, cold-start variance)
makes the ids diverge for the WHOLE run — the recorded whole-run
dropout. The ISS-483 "fourth fix" (resolve through `SortedCameras` by
id) did not fix that class — it converted a generation mismatch into an
id coin-flip and masked the real defect: a cross-WORLD entity identity
confusion. Uniform, upload, and pipeline sides were never at fault.

## Fix (landed 2026-08-05)

Bevy shape (`bevy_pbr/src/fog.rs`): `prepare_fog` writes the offset on
the RENDER-world view entity and the pass reads it from that same view.

- `pbr/render_execute_camera_main_pass.mbt`: the main pass now passes
  `extracted_camera.entity.render_entity` (the authoritative same-frame
  link, exactly like the neighbouring cluster-buffer call) to
  `render3d_prepare_camera_fog_binding`.
- `pbr/fog.mbt`: the resolver reads `ViewFogUniformOffset` directly off
  the passed render-world entity; the `SortedCameras` id-scan is
  DELETED (it was a workaround; comment now records the world-identity
  contract).

## Impact

- (Historical) The atmospheric_fog byte gate (`aaacaca88b53a7e6...`) was
  UNSTABLE until the fix landed; single captures of DistanceFog scenes
  could silently render fog-less. RESOLVED — the gate is byte-stable
  across 10 consecutive runs post-fix.
- Residual pattern to watch: any pass-side consumer that matches a
  MAIN-world camera handle against RENDER-world entity lists by id
  repeats this bug class. `contact_shadows` has the same prepare-side
  shape but no cross-world read site today (its offset component has no
  consumer yet); wire its reader through the extracted camera's
  `render_entity` when it lands.
