## Destination

Produce an implementation-ready architecture decision and migration
specification for a unified `World` with ECS-A and ECS-B component categories,
including public semantics, interoperability, change detection, scheduling,
lifecycle, compatibility, and measurable acceptance gates. The final decision
may reject ECS-B.

## Notes

- This map plans the change; it does not implement ECS-B.
- Fixed inputs from charting: ECS-A and ECS-B share one `World`; mixed queries
  are required; ECS-B enrollment is explicit and permanent for a component
  definition.
- ECS-A accepts arbitrary MoonBit component types and relies on explicitly
  declared query access. ECS-B accepts only valtypes and must use copy and
  replacement semantics to make read and write access enforceable by the API.
- Every session should consult the `wayfinder`, `grilling`, and
  `domain-modeling` skills and preserve the repository's Bevy Replication and
  Runtime Parity Priority vocabulary.
- Tracker operations are documented in [Wayfinding operations](WAYFINDING.md).

## Not yet specified

- The exact typed storage kernel, column representation, and generated query
  arities depend on the public component and query model.
- The observer, hook, removal, and changed-message implementation shape depends
  on the chosen write and change-detection semantics.
- The source-by-source migration order and representative example matrix depend
  on the compatibility boundary and acceptance gates.
- Whether a limited prototype must precede implementation planning depends on
  the MoonBit language-capability research and API decisions.

## Out of scope

- Implementing ECS-B or migrating production components while this map is open.
- Removing ECS-A or forbidding arbitrary MoonBit component types.
- Unrelated render/PBR source-parity work.
- General scheduler parallelization that is not required to make the two
  component categories safe and semantically honest.
