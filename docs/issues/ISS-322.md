## Description
Bevy's glTF light import branch invokes extension callbacks after spawning
directional, point, and spot lights. Mgstudio's current glTF extension handler
API does not expose equivalent light-spawn callbacks, so general source-level
parity for glTF extension participation is incomplete even though
`VolumetricFogExample.glb` does not depend on those callbacks.

## Design
Compare Bevy's `GltfExtensionHandler::on_spawn_light_directional`,
`on_spawn_light_point`, and `on_spawn_light_spot` hooks against mgstudio's
`GltfExtensionHandler`. Add Bevy-shaped callback slots and invoke them from the
glTF light import/spawn path without changing built-in KHR_lights_punctual
semantics.

## Acceptance Criteria
- [x] Bevy source anchors for the three light-spawn extension hooks are listed.
- [x] Mgstudio extension handler API exposes equivalent light-spawn callbacks
      or records a precise blocker if MoonBit cannot express the callback
      shape.
- [x] Mgstudio invokes the callbacks for directional, point, and spot glTF
      lights at the Bevy-equivalent spawn boundary.
- [x] Focused tests prove registered handlers can observe the spawned light
      entity for all three light kinds.

## Close Notes
Closed 2026-07-06. Bevy anchors:
`bevy/crates/bevy_gltf/src/loader/extensions/mod.rs` defines
`GltfExtensionHandler::on_spawn_light_directional`,
`on_spawn_light_point`, and `on_spawn_light_spot`; and
`bevy/crates/bevy_gltf/src/loader/mod.rs` invokes them in the
`KHR_lights_punctual` directional, point, and spot spawn branches before the
generic `on_gltf_node` hook. Mgstudio now exposes equivalent callbacks on
`GltfExtensionHandler`, forwards them through the public glTF extension facade,
preserves the source glTF node index on generated light scene nodes, and
notifies the callbacks from the scene spawn boundary after the concrete light
component is present on the spawned entity.
