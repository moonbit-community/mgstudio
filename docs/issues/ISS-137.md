## Description
`examples/3d/tonemapping` still contains source-shape differences outside the
custom color-gradient material scene:

- Bevy uses `Single<&mut Tonemapping>`, `Single<&mut ColorGrading>`, and
  `Single<&mut Text, Without<SceneNumber>>`; mgstudio currently uses helper
  functions such as `first_entity`, `first2`, and `first3`.
- Bevy's UI authoring is a root `Text::default()` with an absolute `Node`;
  mgstudio currently uses explicit `Camera2d`, `UiRoot`, marker components, and
  child text scaffolding.
- Bevy's image resize system operates on the exact
  `Query<(&MeshMaterial3d<StandardMaterial>, &Mesh3d), With<HDRViewer>>` and
  `Assets<Image>` event ownership. Mgstudio uses local first-match helpers and
  texture-dimension helpers.

ISS-128 restores the previously empty custom-material scene. This issue tracks
the remaining source-shape anchors so they are not mistaken for completed
parity.

## Design
Audit the relevant ECS `Single`, UI ownership, and asset-event/image-size
owners, then simplify the tonemapping example back toward the Bevy source after
the underlying APIs can express it. Do not keep example-local helper functions
as the final parity answer.

## Acceptance Criteria
- [x] The ECS `Single` source shape needed by tonemapping is represented or
      explicitly classified under an ECS API issue.
- [x] The UI authoring shape is resolved through the shared UI/source owner
      rather than tonemapping-local scaffolding.
- [x] Image resize follows Bevy's asset-event and `Assets<Image>` ownership as
      closely as MoonBit can express.
- [x] Tonemapping helper functions that only emulate Bevy `Single` or
      first-match query behavior are removed once the underlying APIs exist.
- [x] A fresh tonemapping reference screenshot is captured after the
      simplification.
