# ISS-164: Route feature-specific StandardMaterial examples through Bevy-shaped feature selection

## Description
ISS-163 completed the shared StandardMaterial optional texture feature-state
plumbing. The remaining gap is end-to-end ownership: examples and runtime setup
must select the Bevy-equivalent feature surface they actually use, and every
consumer of the selected feature state must build matching shader defs,
bind-group layouts, bind-group descriptors, and prepared material payloads.

The audited Bevy examples show different requirements:

- `examples/3d/specular_tint` writes `StandardMaterial::specular_tint_texture`,
  so it requires the `pbr_specular_textures` equivalent.
- `examples/3d/clearcoat` writes `StandardMaterial::clearcoat_normal_texture`,
  so it requires the `pbr_multi_layer_material_textures` equivalent.
- `examples/3d/anisotropy` loads glTF material data whose faithful import
  requires the `pbr_anisotropy_texture` equivalent; its local sphere fallback
  writes only scalar anisotropy fields.
- `examples/3d/transmission` writes scalar `diffuse_transmission` and
  `specular_transmission` fields in this example and does not currently use
  `diffuse_transmission_texture`; screen-space transmission remains a separate
  runtime feature path.

Without an explicit consumer-to-feature route, an example can compile while
silently omitting a gated texture binding from shader defs, bind-group layout,
bind-group descriptor construction, or material uniform flags.

## Design
Add a Bevy-shaped runtime feature-selection path for StandardMaterial optional
texture features:

- Keep `StandardMaterialTextureFeatureSet` as the single source of truth for
  pipeline shader defs, descriptor layout, material bind groups, and prepared
  material payloads.
- Let feature-specific examples declare their required Bevy-equivalent feature
  set at the plugin/app/material owner boundary.
- Thread the selected feature state through the host renderer material
  bind-group construction path; descriptor entries must be included or omitted
  by the same feature gates as `standard_material_bind_group_layout_descriptor`.
- Prefer the Bevy-shaped bindless StandardMaterial route when enabling a
  feature set would exceed non-bindless sampler limits on the current device.
- If the device cannot support the requested feature set, report the same
  explicit unsupported-feature condition added in ISS-163 before GPU pipeline
  creation.

Do not globally enable all optional texture features, collapse bindings, drop
texture fields from examples, or treat a visually plausible scalar-only render
as feature parity.

## Acceptance Criteria
- [x] `examples/3d/specular_tint` selects the `pbr_specular_textures`
      equivalent when it writes `specular_tint_texture`.
- [ ] `examples/3d/clearcoat` selects the
      `pbr_multi_layer_material_textures` equivalent when it writes
      `clearcoat_normal_texture`.
- [ ] `examples/3d/anisotropy` preserves the glTF anisotropy texture route
      using the `pbr_anisotropy_texture` equivalent.
- [ ] `examples/3d/transmission` is documented or wired separately for
      screen-space transmission, without incorrectly enabling
      `pbr_transmission_textures` unless a transmission texture field is used.
- [ ] Feature-specific examples either render through a supported bindless or
      non-bindless feature set, or fail early with the ISS-163
      unsupported-feature error before pipeline creation.
- [x] Host mesh3d material bind-group descriptor construction uses the same
      `StandardMaterialTextureFeatureSet` gates as the StandardMaterial layout;
      `specular_tint` must not hit a bind-group binding-count validation error.
- [ ] Source and screenshot parity are rechecked for the affected examples.
