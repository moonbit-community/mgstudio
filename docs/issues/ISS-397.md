# ISS-397: Stop forcing generic PBR materials through StandardMaterial payloads

## Metadata
- Type: task
- Status: closed
- Priority: 1
- Labels: pbr, materials, standard-material, source-parity
- Assignee: unassigned
- Created: 2026-07-06
- Updated: 2026-07-06
- External ref: none

## Description
The generic `Material` trait currently requires
`standard_material_payload(self) -> StandardMaterial`, so custom PBR materials
must provide a `StandardMaterial`-shaped payload even when Bevy would treat them
as independent material types. This is a local PBR path shortcut, not a MoonBit
language blocker.

## Design
Audit Bevy `bevy_pbr/src/material.rs`, `pbr_material.rs`, and
`extended_material.rs` against mgstudio's `PreparedMaterial[M]` and
`Render3dResolvedMaterial`. Split StandardMaterial-specific shader uniform data
from generic material properties and renderer binding data. Preserve
`StandardMaterial` behavior for real StandardMaterial, but let custom materials
resolve through their own prepared payload and shader/binding data.

## Acceptance Criteria
- [x] `Material` no longer requires `standard_material_payload` for all
      material types.
- [x] `StandardMaterial` still provides the full existing PBR payload path.
- [x] Custom material tests prove a non-StandardMaterial material can prepare,
      specialize, and queue without manufacturing a fake StandardMaterial.
- [x] Shadow and prepass readiness still follow Bevy's `Material::enable_*`
      hooks.
- [x] Targeted material and at least one 3D material visual gate pass.

## Notes
- 2026-07-06: This is expected to be the largest local material cleanup because
  renderer draw payloads currently carry StandardMaterial fields deeply into the
  PBR draw path.
- 2026-07-06: Started after ISS-396. Initial audit found the local shortcut is
  broader than the `Material` trait: `PreparedMaterial`,
  `Render3dResolvedMaterial`, `Render3dResolvedMeshMaterial`,
  `Mesh3dExtractedPayload`, and main-pass draw payload construction all assume
  every material can be represented as `StandardMaterial`.
- 2026-07-06: Removed `standard_material_payload` from the `Material` trait and
  replaced the prepared/resolved/extracted middle layers with
  `MaterialDrawData3d`. Custom material preparation now stores
  `MaterialDrawData3d::Custom`, and StandardMaterial / ExtendedMaterial keep
  explicit `MaterialDrawData3d::Standard` data. Remaining gap: the final host
  draw payload still has legacy StandardMaterial-shaped fields, so custom
  material queue/draw parity is not complete enough to close this issue.
- 2026-07-06: Verified with `moon -C mgstudio-engine test
  pbr/material_plugin_wbtest.mbt --release`, `moon -C mgstudio-engine test
  pbr/pbr_material_test.mbt --release`, `moon -C mgstudio-engine test
  pbr/mesh_flags_wbtest.mbt --release`, `moon -C mgstudio-engine test
  pbr/materials_plugin_wbtest.mbt --release`, `moon -C mgstudio-engine fmt`,
  `moon -C mgstudio-engine info`, `moon -C mgstudio-engine check`, and
  `MGSTUDIO_PARITY_CAPTURE_DELAY_FRAMES=90
  MGSTUDIO_PARITY_RUN_TIMEOUT_SECONDS=240
  mgstudio-engine/scripts/p0_visual_capture_native.sh examples/3d/lines
  /tmp/mgstudio_iss397_lines.png`.
- 2026-07-06: Removed the final `standard_material_for_legacy_host_draw`
  path. `Render3dDrawMaterialInput` now carries the host draw fields that were
  previously read directly from `StandardMaterial`; StandardMaterial builds the
  full input from its own fields, while custom materials build input from
  `MaterialProperties` and their real material bind group data.
