## Description
Bevy can distinguish concrete generic component and resource types through Rust
type identity. MoonBit cannot reproduce that mechanism directly, so mgstudio
uses explicit typed keys and key providers. Without a single convention,
generic resource/component families tend to invent local key-pack patterns and
make future ports harder to audit.

## Design
Document and apply a standard key-family pattern for generic ECS types. The
pattern should keep typed-key storage as the source of truth and avoid erased
payloads, JSON codecs, downcast-style lookup, or integer-id-to-key recovery.
When a Bevy generic family cannot be represented in MoonBit, record a blocker
instead of adding a workaround.

## Acceptance Criteria
- [ ] ECS documentation describes the standard way to expose keys for generic
      resource and component families.
- [ ] Existing generic ECS key-family patterns in active render/PBR/mesh code
      are audited and either aligned or tracked by follow-up issues.
- [ ] New generic component/resource ports have a consistent provider naming
      and registration shape.
- [ ] No JSON-backed or erased runtime payload path is introduced for generic
      ECS values.

## Close Notes
- 2026-06-04: Documented the standard generic key-family provider pattern in
  `mgstudio-engine/ecs/README.md`. Audited active render/PBR/mesh generic
  families: `AssetResourceKeys[T]`, `RenderAssetResourceKeys[A]`, and
  `Material2dKeys[M]` already follow stable typed key-pack providers; render
  `ErasedRenderAssets[A]` is the Bevy-shaped render-asset resource, not a
  JSON-backed ECS payload workaround. `StorageBuffer[Float]` is an explicit
  concrete asset specialization and does not require a blocker.
