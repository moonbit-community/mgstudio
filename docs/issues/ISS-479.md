# ISS-479: Cameras sharing a render target do not compose

## Metadata
- Type: bug
- Status: in_progress
- Priority: 1
- Labels: render, camera, core_pipeline, render-target, source-parity, bevy-sync
- Assignee: unassigned
- Created: 2026-08-02
- Updated: 2026-08-02
- External ref: none

## Description

When two cameras render to the same target and neither restricts itself to a
sub-viewport, only the highest-`order` camera survives in the presented frame.
Every earlier camera's output is discarded.

This is not a clear-colour bug. `ClearColorConfig::None` does not fix it: it
only changes the colour that the surviving camera composites, because the
composite rewrites the whole surface regardless of the load op.

## Evidence

`examples/3d/two_passes` is a checked-in port of `bevy/examples/3d/two_passes.rs`.
Two full-screen cameras view one cube from different angles; the second already
carries `.with_clear_color_config(None)`, exactly as Bevy does.

Captured at frame 90, native release:

| example | distinct colours in frame | expected |
| --- | ---: | --- |
| `examples/3d/two_passes` | **1** (uniform `(43,44,47)`) | two overlapping cube renderings |

The frame is empty. Neither camera's cube is visible. The example has been
silently wrong; nothing in the suite caught it, because it has no reference
screenshot.

The same defect is what breaks `examples/gizmos/transform_gizmo` (ISS-478). The
transform gizmo's overlay camera is `order: 1` on render layer 15, so the main
camera's entire scene is discarded and only the gizmo reaches the screen.
Removing the overlay camera makes the scene render correctly:

| transform_gizmo variant | distinct colours | scene visible |
| --- | ---: | --- |
| as committed (overlay `order: 1`, default clear) | 20 | no |
| overlay camera with `ClearColorConfig::None` | 20 (background turns black) | no |
| overlay camera not spawned | 111 | **yes** |

## Root cause

`pbr/render_execute_camera.mbt:406` allocates the intermediate post-process
target through

    render3d_motion_blur_targets_get_or_create(world, camera_entity, ...)

keyed by **camera entity**. Every camera therefore gets its own scene/HDR
texture, and each one composites that texture over the full surface at the end
of its own pass chain. The last camera to run overwrites everything before it.

Bevy keys the same allocation by **render target**. `prepare_view_targets`
looks textures up by the target/size/format tuple, so all cameras drawing to one
window share a single `ViewTarget`; camera 1 renders into the very texture
camera 0 already wrote. Clearing is then handled once per frame by
`ColorAttachment`, which issues `LoadOp::Clear` on the first write of a frame and
`LoadOp::Load` afterwards. That is why Bevy's own
`bevy_gizmos_render/src/transform_gizmo_render.rs:339` can leave `clear_color` at
its default and still compose correctly.

mgstudio already has the once-per-frame half of this: `cleared_targets_this_frame`
is created per frame in `pbr/render_execute_render_cameras.mbt:51` and threaded
through `render3d_pass_clear_enabled_for_target`. That guard is correct but
ineffective here, because the two cameras never name the same target id, so the
"already cleared" test never matches.

The fix is the sharing, not the clearing: intermediate targets must be keyed by
render target rather than by camera entity, so cameras on one window accumulate
into a single texture.

## Correction: two defects, not one

The `two_passes` blank frame was **not** caused by the composition gap alone. It
was caused by a regression introduced with the transform gizmo render port
(`3feabe828`).

Bevy gates the gizmo spawn:

    spawn_gizmo_meshes.run_if(resource_exists::<TransformGizmoSettings>)

`TransformGizmoSettings` is inserted by `TransformGizmoPlugin`, which an app opts
into. An app that never adds that plugin gets no gizmo meshes and, crucially, no
overlay camera. The port dropped the condition, so **every** app built on
`DefaultPlugins` gained a second order-1 camera on the primary window. Combined
with the composition gap, that blanked or corrupted every 3d example, not just
the two named here. The guard is restored.

So:

- **Regression** -- unconditional overlay camera in every app. Fixed.
- **Engine gap** -- cameras sharing a target do not compose. Fixed for the
  colour path; see Status below.

## Status

Fixed so far:

- `MotionBlurTargetsEntry` is keyed by `render_target_id` instead of by camera
  entity, so cameras sharing a window share one intermediate colour texture.
- The depth load op is decoupled from the colour load op. `begin_pass_3d` takes
  `depth_clear_enabled` (`-1` keeps the legacy "follow colour" behaviour), and
  the 3d main pass passes `1`: depth clears for every camera, matching Bevy's
  `Camera3d::depth_load_op` default of `Clear`. Without this a later camera
  depth tests against the earlier camera's scene and is rejected -- the first
  attempt tied depth to the colour flag and `two_passes` rendered only one view.
- `spawn_gizmo_meshes` is gated on `TransformGizmoSettings`.

Verified by fixed-frame native capture:

| example | before | after |
| --- | ---: | ---: |
| `examples/3d/two_passes` | 1 distinct colour (blank) | 873, both camera views composited, with shadows |
| `examples/3d/3d_scene` (single camera, regression check) | -- | 652, renders correctly; now 1 camera, not 2 |

Still broken:

- `examples/gizmos/transform_gizmo` renders the scene but with what looks like a
  far too narrow horizontal field of view: the ground is a thin vertical band,
  the table is edge-on, and the standalone cube at `x = +2` is outside the frame
  entirely. The gizmo itself draws correctly and in the right place. Both
  cameras report the same target, the same `scene_target`, the same
  `2560x1440` view and the same full-screen viewport, so this is not target
  selection, clearing or viewport. Not yet root-caused; the likely area is the
  per-camera view/projection uniform binding now that two cameras write one
  target.
- `Camera3d::depth_load_op` is still not carried on the extracted view payload,
  so a non-default value cannot be honoured. Every camera clears depth.

## Why this matters beyond the two examples

Camera composition is load-bearing for a large amount of Bevy behaviour that is
otherwise already ported: overlay/HUD cameras, `RenderLayers` split rendering,
UI cameras drawn over 3d, and any multi-pass effect that relies on a second
camera on the same target. Each of those will present only its last camera until
this is fixed. `examples/3d/split_screen` is unaffected only because its four
cameras each own a disjoint sub-viewport.

## Acceptance Criteria
- [x] Intermediate post-process targets are keyed by render target, not by
  camera entity, so cameras sharing a target share textures.
- [x] The first camera writing a target in a frame clears it; later cameras
  load, matching Bevy's `ColorAttachment`.
- [x] Depth clears per camera, independently of the colour load op.
- [x] `spawn_gizmo_meshes` is gated on `TransformGizmoSettings`, so apps that do
  not opt into the transform gizmo get no overlay camera.
- [x] `examples/3d/two_passes` shows both cameras' renderings.
- [ ] `examples/3d/two_passes` compared against the pinned Bevy example.
- [ ] `Camera3d::depth_load_op` carried on the extracted view payload and
  honoured.
- [ ] `examples/gizmos/transform_gizmo` shows the scene and the gizmo together
  with the overlay camera spawned exactly as Bevy spawns it.
- [ ] `examples/3d/split_screen` still renders four viewports.
- [ ] A regression test covers two full-screen cameras on one target.
