# ISS-472: Restrict filtered table batches to matching rows

## Metadata
- Type: bug
- Status: closed
- Priority: 0
- Labels: ecs, table-batch, query-filter, changed, added, capability, correctness
- Assignee: codex

## Description

`Query::try_for_each_filtered_table` evaluates its exact `Changed`, `Added`,
`Or`, or custom row matcher only inside `QueryTableRows::for_each`. The
accompanying `QueryTableBatch` still binds the complete physical table, and
row-level `TableBatchWrite` methods validate only the physical row bounds.
User code can therefore call `set`, `modify`, bypass replacement, or change
metadata methods with a row that does not satisfy the filter and mutate an
entity the query did not yield.

## Design

Make `QueryTableRows::for_each` the row-capability boundary for filtered table
batches. While it invokes the callback for one matching physical row, record
that row as authorized in the shared `QueryTableBatchScope`; restore the prior
authorization with `defer` so raising and nested traversal remain correct.
Every row-level entity/component access must validate the authorization through
the shared scope. `TableBatchChangeWriter` must retain the same scope rather
than validating only physical bounds.

Whole-table batches keep their existing direct physical-row path with no
matcher evaluation. Do not rerun the filter matcher inside every component
access and do not allocate a per-table row mask.

## Acceptance Criteria

- [x] A filtered batch cannot write or mark a physical row that is not the
      currently yielded matching row.
- [x] The currently yielded matching row remains readable and writable through
      all ordinary row-level APIs.
- [x] Authorization is restored after nested traversal and after a callback
      raises.
- [x] Whole-table batches retain unrestricted live-row access.
- [x] Existing production filtered-table call sites require no migration.
- [x] Focused tests run one at a time with `MOONBIT_NEW_NATIVE=1`.
- [x] The generated public interface remains unchanged.

## Notes

- 2026-07-19: Current production filtered-table writers in sprite, transform,
  visibility, and PBR already mutate only the physical row passed by
  `QueryTableRows::for_each`.
- 2026-07-19: Before the repair, the focused reproduction started with one
  `Changed<TableBatchPosition>` row, wrote the other in-bounds physical row,
  and observed `2` visits instead of `1`: the unauthorized write changed the
  filter result while the same traversal was still running.
- 2026-07-19: The retained implementation grants only the currently yielded
  row in the shared scope and restores the prior grant with `defer`. All
  row-indexed table access reaches the central scope check; the separately
  bound `TableBatchChangeWriter` now retains and validates the same scope.
- 2026-07-19: This is a behavioral correction without a public signature
  change. The previously out-of-contract arbitrary-row use now aborts, and the
  supported migration is recorded in `docs/ECS_PERFORMANCE_API_MIGRATION.md`.
- 2026-07-19: A same-machine native-release whole-table accessor benchmark
  measured the pre-repair HEAD at `564.76 us` and `554.92 us` across two runs.
  The repaired branch's stable repeat measured `557.68 us`; its first run was
  discarded as noisy because `186.54 us` standard deviation and a `1.20 ms`
  maximum made the mean non-comparable. The bound read-view control measured
  `62.74 us` before and `61.94 us` after. The predictable whole-table
  short-circuit adds no measurable regression.

## Close Notes

Closed on 2026-07-19. Focused native-release tests independently cover
unmatched write rejection, matching-row mutation, change-writer rejection,
nested and raising callback restoration, unrestricted whole-table mutation,
and the production Sprite bounds filtered writer. The implementation does not
rerun the row matcher for component access and does not allocate a row mask.
`moon check ecs --target native --deny-warn` passes, and `moon info ecs
--target native` confirms that the generated public interface is unchanged.
