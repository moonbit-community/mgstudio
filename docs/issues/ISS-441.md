# ISS-441: Make many_foxes profiling survive long native compilation

## Metadata
- Type: bug
- Status: open

- Assignee: unassigned
- Created: 2026-07-15
- Updated: 2026-07-15
- External ref: none

## Description
`scripts/profile_many_foxes_breakdown.sh` starts the example through `moon run`
after an explicit `moon build`. On the new native toolchain, `moon run` can
recompile the large generated C file for longer than
`MGSTUDIO_MANY_FOXES_START_TIMEOUT_SECONDS`. When that happens, the process
detection loop expires and the script executes `wait "$runner_pid"`; the
example may start afterward and run indefinitely because the normal sampling
and kill path is never reached.

The 2026-07-15 visibility profile reproduced this with a 180-second timeout:
the example started after the deadline, produced a valid trace, and had to be
terminated manually before `analyze_timeline_trace.py` could consume it.

## Design
Keep the normal `moon run` command path, but make timeout cleanup deterministic.
If startup detection expires, terminate the runner process tree and any newly
created `many_foxes.exe` before waiting. Prefer avoiding the duplicate native
compile when the built artifact can be proven current without weakening the
stale-executable guard.

## Acceptance Criteria
- [ ] A startup timeout terminates the runner and any example process instead of waiting indefinitely.
- [ ] A native compile that finishes after the timeout cannot leave `many_foxes.exe` running.
- [ ] A normal successful profile still produces log, trace, Markdown, and CSV artifacts.
- [ ] Cleanup does not terminate a pre-existing `many_foxes.exe` process.
