# ISS-467: Restore component membership updates on despawn

## Metadata
- Type: bug
- Status: closed
- Priority: 0
- Labels: ecs, despawn, archetype, change-detection, correctness
- Assignee: codex
- Created: 2026-07-18
- Updated: 2026-07-18
- External ref: none

## Description

Despawn removes component payloads and then invalidates the entity before
clearing its archetype tracking. Since ISS-452 made
`entity_local_components` resolve membership through the live entity's current
archetype, the post-despawn lookup returns an empty component list. Archetype
and table rows are still removed from their explicitly tracked locations, but
component membership counts and per-component generations are never updated.

The stale count makes `World::component_count` and production conditions such
as `app::any_with_component` report components that no live entity owns. The
stale generation also violates query-cache invalidation invariants.

## Design

Preserve the pinned Bevy invariant that the old entity location/archetype and
its component set remain authoritative throughout structural teardown. In the
MoonBit transaction, clear archetype tracking and update the membership side
indexes while the entity is still live, after observers/hooks and payload
removal but before `Entities::despawn` invalidates the generation. Do not add a
second component-membership index or repair counts heuristically.

## Acceptance Criteria

- [x] Despawning the last owner decrements `component_count` to zero.
- [x] Despawn increments each removed component's membership generation once.
- [x] `any_with_component` becomes false after its last matching entity is
      despawned.
- [x] Table/archetype swap-remove and entity ID reuse remain correct.
- [x] Focused tests run one at a time with `MOONBIT_NEW_NATIVE=1` and the ECS
      public interface remains unchanged.

## Notes

- 2026-07-18: Source trace confirmed that the despawn transaction captures the
  component set while live, but `clear_entity_archetype_tracking` independently
  recomputes it after entity invalidation.
- 2026-07-18: Before the fix, the focused ECS regression observed
  `(component_count=1, generation_delta=0)` after despawning the last owner,
  and the `any_with_component` production regression ran its guarded system a
  second time.

## Close Notes

Closed on 2026-07-18. `commit_component_despawn_transaction` now clears the
entity's archetype/table tracking while the entity is still live, immediately
before `Entities::despawn`. This lets the existing archetype-owned membership
lookup decrement every component count and bump every component generation
exactly once. Hook, observer, payload-removal, allocator, and public API order
remain otherwise unchanged.

The focused count/generation and `any_with_component` tests failed before the
fix and passed afterward. Existing archetype swap-remove and entity-ID reuse
tests also passed separately. All MoonBit commands used
`MOONBIT_NEW_NATIVE=1`; `moon check ecs` completed with zero warnings and
errors, `moon check app` retained only four pre-existing warning-0083 instances,
and `moon info` produced no ECS or app interface diff.
