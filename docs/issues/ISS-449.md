# ISS-449: Remove per-row query wrapper allocation

## Metadata
- Type: task
- Status: closed
- Priority: 0
- Labels: ecs, performance, query, allocation, batch
- Assignee: codex
- Created: 2026-07-15
- Updated: 2026-07-15
- External ref: none

## Description

Complex queries materialize ordinary MoonBit `Read`, `Write`, `Optional`,
`Has`, fetch-context, and tuple objects per entity. Test a table cursor or batch
item boundary that reuses fetch state and only materializes ownership-bearing
objects when the public API requires them.

## Design

Add an explicit ECS-A table-batch traversal alongside the existing row-query
API. The query data and filter remain the authority for component read/write
access and matching-table selection. A batch callback may bind only components
declared by that query, and writable columns expose `set`, `modify`,
`set_if_neq`, and `bypass_change_detection` operations rather than an unchecked
mutable array view.

The first implementation is intentionally limited to dense query data with no
per-row filter. Unsupported sparse or tick-filtered queries must fail
explicitly instead of silently widening their result set. The first production
migration is `reset_view_visibility_system`, measured only through
`examples/stress_tests/many_sprites`. If the retained path meets the ISS-444
gate, follow-up issues may migrate other trace-proven hot call sites one at a
time with separate example gates and commits.

## Acceptance Criteria

- [x] A native profile identifies the measured per-row allocation classes
      before implementation.
- [x] The optimized path removes or amortizes those allocations without
      weakening access validation.
- [x] One focused ECS query test runs at a time with
      `MOONBIT_NEW_NATIVE=1`.
- [x] `examples/stress_tests/many_sprites` is the only runtime performance gate.
- [x] The retained/rejected decision follows the `ISS-444` experiment protocol.

## Notes

- 2026-07-15: Started after `ISS-448` established a table-bound fetch boundary.
  The first step is measurement, not an API change: inspect native generated C
  and an Allocations trace for the fixed `many_sprites` gate to distinguish
  result tuples, `Read`/`Write` wrappers, closure environments, and unrelated
  component-value allocations.
- 2026-07-15: The native generated C for the 20,000-row mutable tuple query
  confirms at least four ECS-owned heap objects per row: the outer
  `(Entity, D)` result, the query-data tuple, `Write`, and `Read`. The same
  benchmark reported about `6.0 GiB` of cumulative mimalloc traffic over its
  approximately 10.5-second run. A user closure captured by `Write::modify`
  adds another allocation, but that is outside ECS ownership. Instruments'
  Allocations template could not attach to the process, and `malloc_history`
  cannot inspect MoonBit's mimalloc zone, so generated native C plus mimalloc
  totals are the allocation evidence for this experiment.
- 2026-07-15: Retained phase one. Dense `Query::view`/`for_each` now advances a
  table cursor and invokes the visitor directly, avoiding the outer
  `(Entity, D)` object that only the iterator API requires. `QueryMany::fetch_next`
  still returns the same public result and keeps its allocation. Generated C
  confirms that the dense visitor path contains no outer-result allocation.
- 2026-07-15: The direct dense query benchmark moved from `2.91 ms` to
  `2.95 ms` (`1.37%` regression), so this is not a speed win. In the sole
  `many_sprites` runtime gate, identically filtered average frame time moved
  from `145.485 ms` to `149.598 ms` (`2.83%` regression), while p50 improved
  from `145.252 ms` to `143.919 ms` and Main improved from `123.219 ms` to
  `122.863 ms`. The change is retained only under the measured-allocation-class
  branch of the `ISS-444` protocol; the remaining per-row data and access
  wrappers are still unresolved.
- 2026-07-15: Current MoonBit still rejects `#valtype` on `ReadValue[T]` with
  compiler error 4173 because the struct contains its type parameter. `ISS-455`
  records this hard external blocker for making the existing generic row-item
  API allocation-free. ISS-449 may still test an explicit table-batch API; it
  must not reuse mutable row wrappers and change their retention semantics.
- 2026-07-15: The user authorized an explicit ECS-A table-batch API and, only
  if the first measured migration is retained, migration of the remaining
  performance-sensitive call sites. The pre-implementation native mutable
  iterator benchmark measured `4.08 ms` for 20,000 rows. The existing
  `many_sprites` trace identifies `reset_view_visibility_system` as the first
  narrow production gate at `10.685 ms/frame`; its query has one writable
  table component and an archetypal `Without` filter.
- 2026-07-15: Retained the generic dense `Query::for_each_table` API for the
  isolated gate. Query data and filters remain the access/matching authority;
  each callback binds typed read/write columns once per table, while writes
  retain `Write`-equivalent change ticks, changed messages, caller metadata,
  and bypass semantics. Sparse data and per-row filters fail explicitly.
  Callback-scoped leases and column bindings are invalidated with `defer` so a
  retained batch wrapper cannot keep using its World or typed column.
- 2026-07-15: The focused dense write/filter/change-detection test passed with
  `MOONBIT_NEW_NATIVE=1`. On the same 20,000-row `(Write, Read)` workload, the
  row `for_each` path measured `4.13 ms` and the table-batch path measured
  `3.27 ms`, a `20.82%` improvement. This exceeds the 5% isolated retention
  gate; the production decision still requires the sole `many_sprites` gate.
- 2026-07-15: Corrected `TableBatchWrite` replacement semantics before the
  production decision. `set` and `bypass_change_detection` now route through
  the same storage replacement/finalizer authority as ordinary `Write`; a
  focused finalizer test proves replaced component values are finalized. With
  that correction, the 20,000-row row path measured `3.94 ms` and the batch
  path `3.04 ms`, a `22.84%` improvement.
- 2026-07-15: Retained the first production migration in
  `reset_view_visibility_system`. Against the two row-query traces, its system
  time moved from `10.539-10.685 ms/frame` to `8.180 ms/frame`, a
  `22.38-23.44%` improvement. Steady frame interval moved from
  `145.485-149.598 ms` to `129.528 ms`, a `10.97-13.42%` improvement. The raw
  diagnostics average was rejected because two excluded runtime stalls of
  `1.408 s` and `2.983 s` contaminated it; all retained numbers use the same
  trace-analysis startup/spike filter.
- 2026-07-15: The focused ViewVisibility semantic-transition test passed. A
  fresh fixed-frame `examples/2d/bloom_2d` row/batch A/B produced byte-identical
  PNGs (SHA-256
  `b9ac5ed0496e93b78a0207f59387d5db40b6bdc6302a41f0f68ddc2d99901f35`),
  providing a separate visual correctness check without using it as the
  runtime performance gate.

## Close Notes

Retained dense table-batch traversal and migrated the first trace-proven
production hotspot. The API amortizes `Read`/`Write` materialization at the
table boundary, preserves query access/filter authority, callback-scoped
leases, change detection, changed messages, caller metadata, and component
replacement finalizers. Additional hotspots must be migrated independently
with their own trace evidence, example, semantic test, and commit.
