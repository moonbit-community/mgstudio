# ISS-497: Legacy untyped MeshMaterial3d is a dead carrier — readers silently no-op

## Description

Commit `05a64d8d5` ("Port scene glTF materials to typed carrier")
switched the glTF scene spawner to the typed
`MeshMaterial3dTyped[StandardMaterial]` component (Bevy's actual shape —
Bevy has only the typed `MeshMaterial3d<M>`), and `pbr/bundles.mbt`
writes the typed carrier as well. The legacy untyped
`@pbr.MeshMaterial3d` component is now written by NOTHING in the engine
(the meshlet example sets it manually — the sole writer). Every
remaining reader silently matches zero entities, the exact failure class
that blacked out the lightmaps example (ISS-488, root cause 1).

Known readers of the dead untyped component:

1. **Examples** querying `@ecs.Read[@pbr.MeshMaterial3d]` (grep hit
   list; each needs the ISS-488-style port to the typed query, and each
   may be silently missing behavior today):
   depth_of_field, animated_material, anisotropy, mixed_lighting,
   specular_tint, blend_modes, tonemapping, reflection_probes,
   transmission (lightmaps already fixed in `c7d6611d0`; mirror fixed
   in `d2fcd718c`).
   ADDITIONALLY (confirmed via ISS-493, 2026-08-07): examples that
   SPAWN entities with the untyped carrier plus
   `.with_extended_material(...)` are fully invisible to
   specialization/queueing — the mirror was the first proven victim
   (queue guard `fail=pipeline-id` forever). The ssr example's water
   surface uses the same dead pattern (`examples/3d/ssr/main.mbt:829`)
   and needs the same typed `ExtendedMaterial` port (atmosphere's Water
   material is the working idiom); survey clustered_decals' usage too.
2. **Engine**: `pbr/render_extract.mbt`'s erased
   `collect_entities_needing_material_specialization` (+ `_removed`)
   gates on `get_by_key(entity, ecs_key_mesh_material3d)` — dead for all
   glTF/bundle content; the per-M typed path
   (`check_typed_entities_needing_specialization_system`) is the live
   Bevy-shaped implementation, so the erased collector is a legacy
   compatibility layer eligible for deletion per the parity skill rule.
3. **Engine**: `pbr/render_execute_mesh_collect.mbt`'s fast query reads
   `@ecs.Optional[MeshMaterial3d]` and the slow path
   `get_by_key(entity, ecs_key_mesh_material3d)` — always None for
   glTF/bundle content; material resolution falls through to the typed
   registry, which works but leaves the untyped branch as dead code.
4. **Example + engine (CONFIRMED via ISS-492 probes, 2026-08-06)**:
   examples/3d/meshlet writes the untyped key manually for its debug
   bunnies, and `pbr/meshlet/top.mbt::meshlet_extract_entities_system`
   REQUIRES the untyped component — probes showed only 5 of 10 meshlet
   instances extract (the typed-carrier bunnies are skipped). Bevy
   resolves meshlet materials from the erased `RenderMaterialInstances`
   (`meshlet/instance_manager.rs`), never from a component. Port the
   extract to that shape (needs the erased id → material family/extension
   resolution, i.e. the family-shim retirement) and move the example's
   debug material to a typed carrier. ISS-492 is blocked on a wgpu-native
   capability regardless, so this fix lands with the family-shim work,
   not as a standalone patch.
