# ISS-463: Diagnose the many_animated_sprites severe performance gap

## Description

After ISS-462 aligned `many_animated_sprites` with the pinned Bevy source,
comparable native-release runs show a severe performance gap on the same
102,400-sprite, 1920-by-1080, scale-factor-1.0, no-vsync workload.

Mgstudio's final diagnostic window reported `8.0271 FPS` average and a current
frame time of `121.4127 ms`. Pinned Bevy reported `410.3411 FPS` average and a
`2.7629 ms` average frame time. The FPS ratio is `51.12x`.

The state is `CAUSE_UNVERIFIED`. Source alignment rules out the previous
example-shape mismatch, but the measurement does not identify whether the
dominant gap belongs to ECS animation writes, transform/visibility work,
render-world extraction, sprite preparation/queueing, draw submission, or
another boundary.

## Design

Follow trace-first performance diagnosis:

- collect reusable mgstudio schedule/system/render traces after initialization;
- measure the animation, transform propagation, visibility, extraction,
  preparation, queue, and render boundaries separately;
- collect matching pinned-Bevy evidence, using a disposable measurement patch
  only if existing diagnostics cannot expose the required boundary;
- compare work counts as well as time so differences in culling or queued
  sprites cannot masquerade as implementation cost;
- promote a cause only after one boundary explains the measured gap.

Do not restructure the ECS, bypass change detection, disable culling, reduce
the workload, or add a renderer shortcut before the cause is verified.

## Acceptance Criteria

- [ ] A repeatable native-release harness excludes initialization and samples
      the same 102,400-sprite workload in mgstudio and pinned Bevy.
- [ ] Mgstudio evidence separates animation, transform, visibility, extraction,
      preparation, queue, and render costs.
- [ ] Matching Bevy evidence accounts for the same boundaries and work counts.
- [x] At least one evidence-based parity cause explains the severe gap.
- [x] A focused optimization is validated against performance, animation,
      culling, and visual parity gates.
- [ ] Any remaining gap greater than 4x stays explicitly cause-unverified.

- 2026-07-17: Focused, disposable native-release microbenchmarks identified
  four concrete mgstudio performance bugs. All probe code was removed after
  measurement; the source worktree was clean before recording these results.
  First, mgstudio's `Timer::tick` functionally rebuilds a reference-typed
  `Timer`, `Stopwatch`, and multiple `Duration` objects for every entity and
  tick. The normal repeating-timer branch took `977.77 us` for 20,000 timers,
  while an equivalent non-boxed value-state implementation took `21.97 us`, a
  `44.51x` difference. Pinned Bevy's `Timer::tick(&mut self)` and
  `Stopwatch::tick(&mut self)` update inline state in place. This is the primary
  verified cause inside the animation slice and explains the reference-count
  and drop stacks observed by `sample`.
- 2026-07-17: Second, `World::changed_components` scans the entire typed
  component storage, resolves tick metadata through entity/table locations,
  materializes an entity array, and `read()` copies that array. The Sprite
  bounds system then inserts those entities into a HashSet and scans the Sprite
  table again. On 20,000 changed dense components this path took `746.09 us`;
  the existing table-bound `Changed<T>` row filter took `153.77 us`, a `4.85x`
  difference. Pinned Bevy expresses the same work directly as
  `Changed<Sprite>` / `Changed<Anchor>` queries. The manual materialization in
  `sprite_calculate_bounds_2d` is therefore a verified source-parity and
  performance bug, not a required MoonBit adaptation.
- 2026-07-17: Third, Sprite Aabb calculation and comparison use reference-typed
  math temporaries. Constructing and collecting the current
  `Vec3 -> Aabb3d -> Aabb` object chain took `773.00 us` for 20,000 bounds;
  collecting the same six scalar results in a non-boxed value took `85.82 us`,
  a `9.01x` difference. The current equality path calls `center()` and
  `half_size()` twice per Aabb, with each getter constructing intermediate
  `Vec3` values; it took `945.12 us` for 20,000 equal pairs versus `54.41 us`
  for direct stored-field comparison, a `17.37x` difference. Pinned Bevy's
  `Aabb` is `Copy + PartialEq` and stores inline `Vec3A` values. These two probes
  explain material portions of mgstudio's `scan_sprites` and `apply_aabbs`
  spans.
- 2026-07-17: Fourth, dense `Write<T>` table binding obtains a
  `RawTableColumn` and discards it. Every `Write::modify` subsequently resolves
  `World.tables[table_id]`, performs a `RawTable.component_indices` map lookup,
  and then writes the changed tick. A disposable patch carrying the already
  bound column into `Write<T>` reduced the existing 20,000-entity mutable-query
  benchmark from an interleaved `1.54 ms` baseline to `1.44 ms`, about `6.5%`.
  This is a verified but secondary bug. Bevy's `WriteFetch` binds direct value
  and tick slices once per table.
