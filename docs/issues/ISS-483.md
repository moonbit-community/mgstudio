## Description

`examples/3d/atmospheric_fog` diverges drastically from the pinned Bevy
baseline at the same fixed frame, in two independent ways:

1. **Terrain color is missing.** Bevy renders green grassy slopes with white
   snow caps; mgstudio renders the same terrain geometry with lit slopes
   near-white and unlit slopes near-black — the terrain's color contribution
   (texture or vertex colors from `terrain.gltf`) is not reaching the shaded
   result, while the snow-cap variation still shows.
2. **DistanceFog contributes nothing.** Bevy shows the atmospheric fog
   gradient and a large soft directional-light glow (exponent 30) over the
   sky; mgstudio shows a flat sky exactly matching the unlit sky cuboid's
   `srgb(0.35, 0.48, 0.66)` with no inscattering, no glow, and no distance
   blending on far slopes.

The example's own wiring is correct and Bevy-shaped: it builds
`DistanceFog` via `from_visibility_colors` (Atmospheric falloff) with Bevy's
exact values, and `pbr/fog.mbt` models the `Atmospheric` falloff. The failure
is engine-side and silent — the run log is empty.

The checked-in reference (pre-2026-07-05) shows the same broken rendering,
so this is a longstanding gap, not a fresh regression from the recent render
slices. ISS-110 (closed 2026-06-18) fixed the example's *source shape* and
described the visual behavior as "close" at that time, which the current
output contradicts; whether fog ever rendered correctly needs history
evidence.

Found during the ISS-481 sweep when the human reviewer flagged the capture.
Notably, old-vs-new delta screening would NOT have caught this: the stale
reference is equally fogless, so the capture-vs-reference delta looked like
the benign dither/UI class. Only the pinned-Bevy comparison exposed it.

## Root cause (proven 2026-08-04)

The "two independent failures" framing above was wrong. Instrumented runs
([DEBUG-483] probes at every stage, since removed) proved a SINGLE root
cause with two visible faces:

**Distance fog runs as a CPU per-mesh-center approximation applied to the
material base color before lighting, while the Bevy per-fragment GPU fog
path is severed at the CPU->GPU seam.**

1. The GPU path is dead: `mesh3d_fog_buf` (mesh-view binding 13, 64 bytes,
   `render/renderer/mesh3d_pipeline_build.mbt:911`) is created zero-filled
   and NEVER written — no upload site exists anywhere in the renderer
   (`MESH3D_FOG_BUFFER_SIZE` appears only at constant/create/bind/layout
   sites). The mirrored shader reads mode 0 = `FOG_MODE_OFF`
   (`pbr/render/mesh_view_types.wgsl:108`), so per-fragment fog is
   permanently off. The Bevy-shaped prepare side
   (`render3d_prepare_fog_system` -> `FogMeta.gpu_fogs` ->
   `ViewFogUniformOffset`) runs correctly every frame — probes:
   `fog_bit=true` x33, `has_fog=true` x30 — and nothing consumes it.
2. In its place, the legacy CPU path (`render3d_apply_distance_fog`, in the
   draw loop at `render_execute_camera_main_pass.mbt:726`) applies Bevy's
   atmospheric extinction/inscattering formula at MESH-CENTER granularity
   to the draw's base color. Probe at the terrain draw:
   `dist=1.418  in=0.123,0.357,0.066  out=0.094,0.219,0.361` — the glTF
   green becomes blue-dominant for every fragment of the mesh uniformly,
   BEFORE lighting. Sunlight on that clips lit slopes to (243,255,255)
   (red lowest because the fog color's red 0.35 is lowest) and shaded
   slopes sit at (11,22,30); pinned Bevy at the same pixels shows
   (90,140,83) and (21,39,58). Per-mesh-center fog is structurally unable
   to produce Bevy's distance gradient or the directional-light glow.
3. The material system is fully exonerated — the original "terrain color
   missing" hypothesis is DISPROVEN. Probes showed green surviving every
   stage: glTF parse (`base=0.123,0.357,0.066`), built material, prepared
   asset (`prepare id=3 base=0.123,...`), and the draw
   (`draw std base=0.123,...` for the terrain meshes). `Mountains.gltf`
   carries the green purely as `baseColorFactor` (no textures, no vertex
   colors); the loader, typed-material slots, and draw resolution all
   deliver it intact.
4. Secondary finding: the CPU approximation's per-channel output also
   diverges from what Bevy's shader formula would give at the same
   distance (blue-skewed) — moot, since the path must be deleted, but it
   explains why even near meshes discolor visibly.
5. History: the CPU fold dates to 2026-04-12 (`8fc6e969e`), the buffer to
   2026-04-28 (`7b8adbafa`, mesh-view binding scaffolding, upload never
   implemented). Only 3 commits ever touched the buffer, none adding a
   write. Camera distance fog has therefore NEVER rendered through the
   shader in mgstudio; the example was captured already broken for its
   2026-06-18 reference. This is a never-implemented seam, not a
   regression — ISS-110's "core visual behavior is close" claim was never
   pixel-verified against Bevy.

Ruled out along the way (each falsified by a probe or byte-comparison):
missing/ignored `baseColorFactor`, the glTF material handler gate,
`load_materials` loader settings, the `MaterialDrawData3d::Custom` white
fallback (never fires in this example), asset-store handle collisions, and
plain lighting overexposure.

## Design

Bevy-shaped repair, no workarounds:

1. Implement the missing CPU->GPU seam: upload `FogMeta.gpu_fogs` into the
   per-view fog uniform (binding 13) each frame, addressed by
   `ViewFogUniformOffset`, mirroring Bevy's `prepare_fog` +
   `MeshViewBindGroup` contract.
2. Delete the CPU per-mesh application (`render3d_apply_distance_fog` call
   site, `mesh_distance` computation, and the fogged base-color plumbing in
   the draw payload) so base colors reach the shader unmodified and fog is
   applied per fragment by the mirrored WGSL.
3. Re-verify against the recorded pinned-Bevy artifact
   (`.private/parity/artifacts/atmospheric_fog/bevy_f90_20260804.png`):
   green terrain, distance gradient, and the directional-light glow should
   all appear from the same fix. Then the example re-enters ISS-481.

## Implementation (2026-08-04)

Landed in one slice:

1. The missing CPU->GPU seam: `render/renderer/gpu_distance_fog.mbt` packs
   the 64-byte `Fog` uniform (`u32le_pack`, field order matching
   `mesh_view_types.wgsl`) and writes `mesh3d_fog_buf`;
   `host_gpu_prepare_mesh3d_fog` forwards from the render facade;
   `render3d_prepare_camera_fog_binding` uploads each camera's prepared
   `GpuFog` (via `ViewFogUniformOffset` -> `FogMeta`, `GpuFog::off()` for
   fog-less cameras) next to the other per-camera mesh-view uniforms.
2. The CPU per-mesh family (`render3d_apply_distance_fog`, mix/directional
   helpers, `mesh_distance`, the fogged draw-color plumbing, the dead
   `distance_fog` pass-config field) is deleted; draw payloads carry
   unmodified material base colors.
3. A FOURTH bug found during verification, fixed at the root:
   `fog_falloff_pow_e` computed `e^x` where Bevy computes `x^e`
   (`ops::powf(value, E)`), inflating atmospheric coefficients up to ~7x
   (and the alpha factor e-vs-1). `pbr/fog_test.mbt` now asserts the
   atmospheric_fog example's exact colors derive Bevy's vectors
   (be=[0.149761, 0.103772, 0.051383], bi=[0.050684, 0.070315, 0.199715]).
4. Example source-parity fix: the sky material used the raw `Color::new`
   constructor for Bevy's `Srgba::hex("888888")`, storing 0.5333 as linear;
   now `Color::srgb(0.5333...)`, matching Bevy's conversion.

Verification: `moon check` clean; fog tests pass including the new
coefficient regression; fog-less gates BYTE-IDENTICAL to their canonical
states after the change (ssao 367e3e5647317c41..., motion_blur
e3cc4bf6dbf2b38d...); atmospheric_fog now renders green terrain with
per-fragment fog responding to the Bevy-exact uniform.

Residuals that keep the visual criteria open:

- Unlit materials receive no fog in the renderer: the flat sky proves it,
  while the mirrored `pbr.wgsl:81-89` applies post-lighting processing
  (fog) to unlit materials and the material flags carry
  FOG_ENABLED|UNLIT. Bevy's sky gradient and most of the visible glow are
  fog OVER the gray unlit sky cuboid (`Srgba::hex("888888")`, scale 20 ->
  distances to ~20 units), so visual acceptance depends on this. The
  divergence is in the renderer's unlit draw path variant - next
  diagnosis target.
- Narrowed (2026-08-04, post-fix probes): the unlit-fog loss is inside the
  renderer's shader-composition seam. Probes at the draw loop show the sky
  draw carries `unlit=true fog=true` payload flags and the corrected linear
  base color (0.246), all three draws share pipeline id 0 (one uber
  pipeline, whose fragment path is the mirrored `pbr/render/pbr.wgsl`), the
  terrain fogs through that same pipeline, and the fog uniform is
  Bevy-exact — yet the sky renders unfogged. Everything upstream is
  exonerated; the remaining suspect is how the composed module maps
  per-draw material data into `pbr_input.material.flags` for the unlit
  branch (the payload bit layout matches `pbr_types.wgsl`, so the loss is
  in the composition/adaptation layer, not the bit values). Exposure
  defaults match Bevy (both EV100 9.7 Blender), ruling that out for the
  brightness residual.
- Terrain lit response is ~2.3x brighter than Bevy (near slope
  (87,139,52) vs Bevy (37,61,49); lit slopes clip toward white) -
  exposure/illuminance divergence, separate owner.

## Second fix (2026-08-04): forward pipelines never specialized on view fog

The unlit-fog residual's root cause, proven by elimination and then found
in the compose: `mesh3d_forward_shader_defines` (and the descriptor
variant's fallback) NEVER set `DISTANCE_FOG` — no forward pipeline in the
renderer ever compiled the fog code. Only the deferred-lighting compose set
it (unconditionally), which is why lit geometry appeared to fog (through
the deferred lighting shader) while the unlit sky — forward-rendered, as
in Bevy — never fogged. Bevy specializes every forward pipeline of a
fogged view via the view key's DISTANCE_FOG bit.

Fix: thread `distance_fog` through the forward pipeline chain — cache key
(`Mesh3dPipelineCacheEntry` + custom-pipeline key string), the
get/failed/set/set_failed quartet, both `ensure_mesh3d_pipeline_*`
entries, the define builders (`if distance_fog { DISTANCE_FOG }`), the
custom-pipeline chain, and the meshlet shade path — derived at
`mesh3d_pipeline_for_current_pass` from
`pass_kind_fog_enabled(pass_state.pass_kind)` (the pass kind already
carried the camera's fog state end-to-end). The deferred-lighting compose
now derives the define from the same pass state instead of hardcoding it.
Warmup paths precompile the unfogged variant; fogged variants build on
demand.

Verification: the sky now renders the fog gradient and sun glow — the
blue side is pixel-near Bevy ((79,118,182) vs (78,112,167)) — and the
fog-less gates remain byte-identical (ssao 367e3e5647317c41...,
motion_blur e3cc4bf6dbf2b38d...). The remaining visual delta is the
single known brightness residual (~2.3x), which clips the glow region and
overbrightens lit terrain.
