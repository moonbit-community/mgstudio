## Description

Every frame of `examples/3d/auto_exposure` logs

```
[renderer] apply_auto_exposure: Fatal(wgpu: invalid WGSL IR pipeline: IR
validation failed: invalid IR store target expression type for handle: 4)
```

(77 occurrences in a 90-frame capture), so the auto-exposure compute pass
never executes and the example renders WITHOUT the feature it
demonstrates. The frame otherwise renders and passes image sanity, which
is why the failure went unnoticed until the ISS-481 sweep enforced the
clean-run-log rule.

Pre-existing, not from the ISS-483 tonemapping slice:
`render/renderer/gpu_auto_exposure.mbt` has no commits since the embedded
WGSL refactor era, and the old-vs-new capture delta for the example is
the standard tonemapping class (mean_abs_rgb 14.46, 100% changed, 3.7%
strong) with no exposure-level collapse — both captures share the same
feature-dead state.

Suspect surface: the auto-exposure compute shader's composed WGSL/IR
(store into a storage-buffer/atomic handle) at the WESL/WGSL composition
seam, or a wgpu-native IR validation rule the composed shader violates.
Compare against `bevy/crates/bevy_core_pipeline/src/auto_exposure/`
(`auto_exposure.wgsl`, `AutoExposurePipeline`) per the parity skill.

## Root cause (proven 2026-08-05)

The failure is not in mgstudio at all. The chain:
`apply_auto_exposure` -> `load_wgsl_from_assets_required` -> the
naga_oil-port composer (`Milky2018/moon_wgsl_naga_oil`) -> the
`Milky2018/wgsl` IR validator, which rejects the shader before any
pipeline is created.

`post_process/auto_exposure/auto_exposure.wgsl` is byte-identical to
Bevy's `bevy_post_process/src/auto_exposure/auto_exposure.wgsl` and
stores scalars DIRECTLY into `atomic<u32>` histogram bins
(`histogram_shared[i] = 0u`, `histogram[i] = 0u`, plus plain loads of
the same bins). Naga explicitly permits both relaxations:

- Store: naga-29.0.3 `src/valid/function.rs`, `S::Store` — "The Naga IR
  allows storing a scalar to an atomic."
- Load: `src/proc/typifier.rs` — `Load` through a pointer-to-atomic
  resolves to the underlying scalar.

The MoonBit port had ported the Load half (`load_result_type` unwraps
`Atomic(scalar)`) but not the Store half: `require_store` ran
`type_assignable(atomic<u32>, u32)` = false and raised
`InvalidStoreTarget`. Handle 4 is the `Access` expression into the
histogram array in `compute_histogram` (reproduced at handle 2 in a
minimal repro).

## Fix (landed 2026-08-05, upstream)

Fixed at the owner: the moon_wgsl workspace
(`~/Documents/projects/moon_wgsl`), commit `ad3444c` — `require_store`
now compares the stored value against the atomic's inner scalar type,
scoped to store signatures exactly like naga (the relaxation does NOT
leak into general type compatibility). Regression test added: a
minimal direct-atomic-store shader through parse -> validate AND the
full emit -> reparse -> validate roundtrip.

Validation there: `wgsl/ir` 448/448; full `wgsl`, `moon_wgsl_naga`,
`moon_wgsl_naga_oil`, `moon_wesl` suites all green; `moon check`/`fmt`
clean; no public-API (`.mbti`) change.

RELEASE DEBT: mgstudio consumes `Milky2018/wgsl@0.17.0` from the
registry; the fix is unreleased. Local verification patched the
gitignored `.mooncakes` vendored copy — a fresh dependency re-install
reverts the local build to the broken validator until the next
workspace release (0.17.x) is published and mgstudio's `moon.mod` is
bumped.
