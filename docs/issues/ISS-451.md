## Description

World tables, archetypes, local component metadata, membership generations, and
several structural edges use `Map[Int, ...]` even though their IDs are dense and
monotonic. Replace only profile-proven hot dense-ID maps with direct indexed
arrays; signature-to-ID indexes remain maps.

## Design

Isolate `World.tables` as the first and only registry variable. The pinned Bevy
`Tables` owner stores tables in `Vec<Table>` indexed by `TableId` while keeping
the component-signature-to-ID index as a `HashMap`. Mgstudio will mirror that
split with `Array[RawTable?]`: bounds and `None` preserve explicit missing-ID
semantics, and lazy table construction fills the dense ID slot. No archetype,
component, signature, edge, or membership registry changes belong in this
experiment.

## Acceptance Criteria

- [ ] Only dense-ID registries are converted; associative signature indexes are

## Notes

- 2026-07-16: Source audit found more than forty `table_storage` call sites
  shared by query fetch, filters, component columns, table batches, structural
  moves, and change ticks. The storage owner itself has only four direct Map
  operations (`get`, `get_or_init`, and two iterations), so the registry can be
  isolated without changing callers or table payload ownership.
- 2026-07-16: Pinned Bevy `Tables` uses `Vec<Table>` for `TableId` lookup and a
  separate `HashMap<Box<[ComponentId]>, TableId>` for associative signature
  lookup. Mgstudio's existing `table_ids_by_signature` remains unchanged.
