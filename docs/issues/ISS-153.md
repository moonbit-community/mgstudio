## Description
`ISS-010` added durable counters and re-profiled `mgstudio.render.prepare_meshes`
after the higher-priority many_foxes skinning/render issues were closed. The
current profile still reports `mgstudio.render.prepare_meshes=2.899 ms/frame`
at `1000` foxes.

The counters show that the steady scene mostly hits caches:
`prepared_meshes=1001`, `buffer_uploads=1`, `skipped_unchanged_meshes=1000`,
`mesh_upload_cache_hits=1000`, `mesh_upload_cache_misses=1`,
`preprocess_static_cache_hits=1000`, and `preprocess_static_cache_misses=1`.
The remaining cost is therefore not repeated mesh buffer upload. It is the
source-owner mismatch around mesh extraction, `RenderMesh` preparation,
`MeshAllocator`, and render mesh instance data flow.

## Design
Audit and port the current Bevy mesh preparation owner directly:

- `bevy_render/src/render_asset.rs::prepare_assets::<RenderMesh>`;
- `bevy_render/src/mesh/allocator.rs::MeshAllocator`;
- `bevy_pbr/src/render/mesh.rs` extraction and `RenderMeshInstances`
  preparation paths.

Do not add local shortcuts that skip Bevy-visible state, and do not treat the
existing host mesh upload cache as equivalent to Bevy's render asset allocator
unless the source-shape audit proves it.

## Acceptance Criteria
- [x] Every Bevy source anchor listed in the Design section is classified as

- [x] Mesh preparation counters remain present in the many_foxes profile and

- [x] The `1000`-fox many_foxes release profile reports

      recorded with exact source and profile evidence.
- [x] Relevant `mesh`, `pbr/render`, and `pbr` release tests pass.

## Notes
- 2026-06-24: Created from `ISS-010` after the post-skinning/render profile
  showed prepare_meshes still above `1 ms/frame` despite steady upload and
  preprocess cache hits.
- 2026-06-24: Source anchor classification:
  - `bevy_render/src/render_asset.rs::prepare_assets::<RenderMesh>`:
    `partial`. Mgstudio has the generic
    `mgstudio-engine/render/render_asset.mbt::prepare_render_assets_with`
    control flow, including removed/queued/extracted assets and
    bytes-per-frame retry handling, but `RenderMeshAssets` is still a
    specialized `Map` resource in `mgstudio-engine/render/mesh/top.mbt` and is
    not wired as Bevy's `RenderAssetPlugin::<RenderMesh, GpuImage>` owner.
  - `bevy_render/src/mesh/allocator.rs::MeshAllocator`: `partial`. Mgstudio
    has `mgstudio-engine/render/mesh/allocator.mbt::MeshAllocator` with slab
    state, `allocate_render_mesh`, `free_meshes`, resource keys, and tests, but
    lacks Bevy's `allocate_and_free_meshes` schedule owner over
    `ExtractedAssets<RenderMesh>` and does not make the allocator the sole
    render-asset upload owner.
  - `bevy_pbr/src/render/mesh.rs` extraction and `RenderMeshInstances`
    preparation: `facade`. Mgstudio has
    `mgstudio-engine/pbr/render_mesh_instances.mbt::RenderMeshInstances`, but
    it is a single CPU-style `Map` of queue data. It does not model Bevy's
    `CpuBuilding/GpuBuilding` split, `extract_meshes_for_gpu_building`
    changed-query path, per-worker queues, `MeshesToReextractNextFrame`, or
    `collect_meshes_for_gpu_building` prepared/update fast path.
- 2026-06-24: The current profile at
  `/tmp/mgstudio_many_foxes_iss152_direct_finish_aabb3d/frametime_breakdown.md`
  still reports `mgstudio.render.prepare_meshes=3.034 ms/frame` with
  `prepared_meshes=1001`, `buffer_uploads=1`, `skipped_unchanged_meshes=1000`,
  `mesh_upload_cache_hits=1000`, `mesh_upload_cache_misses=1`,
  `preprocess_static_cache_hits=1000`, and
  `preprocess_static_cache_misses=1`. This proves upload work is separated by
  counters, but the remaining cost is the monolithic PBR extraction/prepare
  owner, not repeated mesh upload.
