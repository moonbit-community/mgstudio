# ISS-394: Retire legacy erased StandardMaterial mesh material authoring

## Description
ISS-236 proved that Bevy-shaped typed `MeshMaterial3d<M>` extraction can drive
StandardMaterial render material instances and shadow/main-pass specialization
without authoring the legacy erased `@pbr.MeshMaterial3d` component. However,
many examples, scene structures, and helper bundles still author or expose the
legacy erased StandardMaterial carrier.

Bevy's source owner is `bevy/crates/bevy_pbr/src/mesh_material.rs`, which has a
single generic `MeshMaterial3d<M>(Handle<M>)`. The remaining erased
StandardMaterial authoring is a local source-parity gap, not an external
blocker.

## Design
Audit every remaining `@pbr.MeshMaterial3d::new` / `ecs_key_mesh_material3d`
authoring path against Bevy source ownership. Migrate StandardMaterial mesh
authoring to typed `MeshMaterial3dTyped[StandardMaterial]` and keep legacy
erased paths only where the audited source owner is a non-StandardMaterial
material-extension bridge with its own tracked parity issue.

Do not add a compatibility layer that writes both components.

## Acceptance Criteria
- [ ] All ordinary StandardMaterial mesh authoring uses the typed
      `MeshMaterial3dTyped[StandardMaterial]` component.
- [x] Scene and glTF StandardMaterial spawn paths no longer require the erased
      `ecs_key_mesh_material3d` component.
- [ ] Any remaining erased material carrier usage is classified by source owner
      as a custom material-extension bridge, blocked owner, or separate open
      parity issue.
- [ ] Targeted PBR/material, scene/glTF, and at least one 3D visual gate pass
      after the migration.
