## Description
`sprite/render2d.mbt` contains a large `render_execute_system` that manually
drives camera item drawing, UI overlay passes, scene passes, scissor handling,
postprocess target allocation, bloom/CAS/tonemapping, and draw dispatch. Bevy's
2D path is instead built from Core2d graph systems, render phases, phase items,
draw commands, render assets, and postprocess nodes.

This immediate-mode execution monolith is a source-level parity gap even if the
final image looks plausible.

## Design
Port the Bevy Core2d execution shape: `Core2d` schedule, `Core2dSystems`,
opaque/alpha-mask/transparent phases, sprite and mesh2d queue systems, draw
commands, and postprocess nodes. The MoonBit implementation can use package
splits, but the runtime ownership must stop centering on one render2d function.

## Acceptance Criteria
- [ ] `render_execute_system` no longer owns the full 2D frame lifecycle.
- [ ] Sprite, mesh2d, UI, and postprocess are consumed through Bevy-shaped phases/nodes rather than one local draw loop.
- [ ] Opaque, alpha-mask, and transparent 2D phase ordering has tests tied to Bevy source behavior.
- [ ] Representative sprite, mesh2d, UI, bloom2d, and render-to-texture examples pass after the change.
