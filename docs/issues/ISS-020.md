# ISS-020: Unblock exact Bevy meshlet visibility-buffer runtime under native WebGPU limits

## Metadata
- Type: task
- Status: blocked
- Priority: 0
- Labels: parity, pbr, meshlet, native-webgpu, external-blocker
- Assignee: unassigned
- Created: 2026-06-02
- Updated: 2026-07-21
- External ref: none

## Description
Mgstudio has ported much of Bevy's meshlet asset, processor, storage-buffer,
descriptor, material-id, and material-shade planning surface. Runtime meshlet
visibility remains unavailable because exact Bevy visibility-buffer resources
need behavior beyond the portable WebGPU C ABI shape used by the current native
MoonBit rendering stack.

This is no longer tracked as an open `wgpu_mbt` repository issue. The historical
upstream requests were closed. `wgpu_mbt@0.15.0` now exposes native immediates
and experimental mesh-shader capability queries, so those surfaces are local
integration work rather than missing dependency APIs. The remaining hard
external gap is the exact Bevy `R64Uint` atomic storage-texture format/access
pair, which the supported native WebGPU C header still cannot express.

## Design
Keep the blocker explicit and do not claim runtime parity until the exact
Bevy visibility-buffer resource shape is available. Do not rewrite the meshlet
algorithm to a different visibility-buffer representation as a local parity
claim. Once an exact native path exists, remove the runtime-unavailable path and
wire Bevy's visibility buffer, material shade pass, and mesh shader capability
checks into the renderer. Use the dependency's current immediates and
mesh-shader queries instead of retaining conservative local placeholders; keep
the runtime disabled until the independent `R64Uint` atomic storage-texture
blocker is actually removed.

## Acceptance Criteria
- [ ] The native MoonBit rendering stack can create the exact Bevy visibility-buffer texture/access combination: `TextureFormat::R64Uint` plus atomic storage texture access for `texture_storage_2d<r64uint, atomic>`.
- [ ] The native MoonBit rendering stack can express bind-group layouts and `IMMEDIATES` or push-constant ranges in the same descriptor shape required by Bevy.
- [ ] Mesh shader capability reporting is available or explicitly mapped to Bevy's adapter requirement checks.
- [ ] Mgstudio removes the meshlet runtime-unavailable gate once dependency support exists.
- [ ] The meshlet example renders with Bevy-equivalent visibility buffer and material-shade output.
- [ ] The roadmap blocker is closed or updated with exact dependency, ABI, or local integration evidence.

  moonbit-community/wgpu-mbt#21 and moonbit-community/wgpu-mbt#22 are closed.
  Treat any remaining work here as mgstudio meshlet-runtime integration or a
  broader native/WebGPU ABI limitation, not as an open `wgpu-mbt` GitHub issue.
- 2026-07-01: Updated the issue wording to remove the stale implication that
  open `wgpu_mbt` repository issues were the current blocker. At that snapshot,
  exact Bevy meshlet visibility-buffer runtime still needed an expressible
  native `R64Uint` atomic storage texture path and matching pipeline-layout
  capabilities; the closed upstream tickets became historical context.
- 2026-07-21: Rechecked the current pinned `wgpu_mbt@0.15.0`. Its public API now
  exposes `Adapter`/`Device` experimental mesh-shader feature queries, native
  immediates feature and limit queries, combined bind-group/immediates pipeline
  layouts, and render/compute pass `set_immediates`. These capabilities must no
  longer be described as absent upstream. Mgstudio already queries native
  immediates but still returns `false` unconditionally from
  `meshlet_adapter_supports_mesh_shader()`, so completing that capability

  `texture_storage_2d<r64uint, atomic>` resource. Mgstudio therefore still
  returns `true` unconditionally from
  `meshlet_missing_native_r64uint_storage_texture_api()` and correctly keeps
  `meshlet_runtime_available()` false. This is the remaining hard blocker.
- 2026-07-21: ISS-402's compiler ICE is closed: the current default native
  backend builds the full meshlet example and completes a standard frame-90
  capture. The resulting image shows only the plane/background and none of
  pinned Bevy's two rows of five bunnies; the checked-in reference is entirely
  black and is not valid parity evidence. This runtime/visual failure belongs
  here and must not be confused with the resolved compiler issue or used to
  refresh the reference.
