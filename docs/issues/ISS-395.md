## Description
The current material system contains several local architecture debts that
should not be treated as MoonBit language blockers. MoonBit does not provide
Rust-style `TypeId`, `Any`, derive macros, or Bevy's exact generic render-asset
machinery, but mgstudio can still avoid local weak abstractions such as public
string-encoded material keys, PBR materials forced through `StandardMaterial`
payload shape, duplicated 2D/3D material runtime registries, and linear
material-type scans during render extraction.

## Design
Keep the typed `Material[M]` and `Material2d[M]` user-facing shape where it is
needed for MoonBit. Move local weak points toward a Bevy-shaped internal
boundary: typed material plugins prepare assets into stable prepared-material
records; render queueing consumes erased or shared material properties and
binding data; material identity is represented by structured keys rather than
ad-hoc strings.

Do not classify these items as external blockers. If a later subtask hits an
actual MoonBit expressibility limit, split that limit into a new blocker issue
with concrete evidence.

## Acceptance Criteria
- [ ] Public material key generation no longer depends on arbitrary string
      encoding supplied by each material implementation.
- [ ] PBR material preparation no longer requires generic materials to masquerade
      as `StandardMaterial` payloads unless the material really is
      `StandardMaterial`.
- [ ] 3D and 2D material runtime registration share a common render-material
      abstraction or have an explicitly documented unavoidable divergence.
- [ ] Render extraction and queueing avoid unindexed linear scans over all
      registered material types where entity-local material identity is already
      known.
- [ ] Each child issue closes with targeted tests and `moon fmt`, `moon info`,
      and `moon check` evidence.
