## Description
Bevy's volumetric fog render path consumes render-world entities and components,
not ad hoc reads from the main world during camera rendering. Before the
extract system can be ported faithfully, mgstudio needs an explicit
render-world storage model for extracted `VolumetricFog`, `FogVolume`,
`VolumetricLight`, and the `GlobalTransform` data used by fog volumes.

## Design
Audit Bevy `bevy_pbr/src/volumetric_fog/render.rs` and the existing mgstudio
render entity mapping. Define the smallest render-world storage shape that can
preserve Bevy's source ownership: camera/view fog is keyed by the render view
entity, fog volumes carry synced transform data, and volumetric lights are
countable before prepare systems run. Do not use JSON payloads, global `Ref`
state, or source-world lookups as storage.

## Acceptance Criteria
- [ ] Render-world storage for volumetric fog views, fog volumes, fog-volume transforms, and volumetric lights is explicit and typed.
- [ ] The storage model records how source entities map to render-world owners.
- [ ] Focused tests can construct render-world volumetric fog state without touching the source world during prepare.
- [ ] The design is documented in issue notes if MoonBit ECS cannot mirror Bevy entity sync exactly.

## Close Notes
2026-07-04: Added the explicit typed render-world storage surface for Bevy
volumetric fog extraction. `pbr/volumetric_fog` now registers the render-world
component set used by this owner: `MainEntity`, `VolumetricFog`, `FogVolume`,
`VolumetricLight`, `GlobalTransform`, `ViewVolumetricFog`, and
`ViewVolumetricFogPipelines`. It also exposes render-world identity and storage
inspection helpers so the next extraction slice can copy and clean up typed ECS
components instead of building a side HashMap or reading the source world during
prepare. Fog volume inputs are read from render-world `FogVolume` plus
`GlobalTransform`, preserving Bevy's storage shape as far as the current
MoonBit ECS sync model allows.
