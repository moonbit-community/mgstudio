## Description
Current Bevy `bevy_pbr/src/ssao/mod.rs` chooses the SSAO intermediate depth
storage format by querying:

`RenderAdapter::get_texture_format_features(TextureFormat::R16Float).allowed_usages.contains(TextureUsages::STORAGE_BINDING)`

Mgstudio currently uses `Milky2018/wgpu_mbt@0.14.6`. The project can request
`NATIVE_FEATURE_TEXTURE_ADAPTER_SPECIFIC_FORMAT_FEATURES`, but local searches
have not found an equivalent per-format feature/usages query. Without that
query, mgstudio cannot source-match Bevy's `R16Float` vs `R32Float` SSAO
depth-format selection.

This should be treated as an API-surface audit first, not automatically as an
open upstream blocker. If the native dependency can already express the query,
wire it locally. If it cannot, split or update this issue with the exact missing
symbol/API and a fresh upstream reference.

## Design
Do not hard-code an adapter assumption in mgstudio and do not probe support by
trying to create a texture. The correct fix is to use a thin safe binding
equivalent to wgpu's texture-format feature query so mgstudio can port Bevy's
`SsaoPipelines::from_world` format decision directly.

## Acceptance Criteria
- [ ] The native dependency surface is audited for an adapter texture-format
      feature/usages query that can answer whether `TextureFormat::R16Float`
      supports `TextureUsages::STORAGE_BINDING`.
- [ ] If the query is missing, a precise upstream dependency issue is filed and
      linked in `External ref`.
- [ ] Mgstudio SSAO selects `R16Float` when the queried allowed usages include
      storage binding and falls back to `R32Float` otherwise.
- [ ] `mgstudio-engine/render/renderer/gpu_ssao.mbt` no longer has a local
      source-parity gap for Bevy's `SsaoPipelines::from_world` depth-format
      detection.
- [ ] Focused SSAO validation and `examples/3d/ssao` capture still pass after
      the query is wired.
