# ISS-259: Prove scrolling_fog directional shadow texture reaches volumetric fog pass

- Updated: 2026-07-05

## Description
A draft `scrolling_fog` runtime gate showed that render-world lighting contains
directional shadow maps and cascades, but the volumetric fog draw path did not
yet prove that it consumes the non-fallback directional shadow texture.

## Design
Diagnose the data path from directional shadow target creation, through camera
shadow bindings, through the main pass or volumetric fog pass state, into the
volumetric fog draw bind group. Read the corresponding Bevy source ownership
before changing mgstudio code. The goal is evidence of real resource propagation,
not a relaxed assertion or fallback-texture acceptance.

## Acceptance Criteria
- [x] A targeted runtime test distinguishes fallback directional shadow texture
      use from the real directional shadow target.
- [x] The test proves `scrolling_fog` reaches the volumetric fog draw path with
      directional shadow maps enabled and at least one cascade.
- [x] The test proves the volumetric fog bind group consumes the non-fallback
      directional shadow texture when directional shadows are enabled.
- [x] If the texture id is lost between Bevy-shaped render owners, the exact
      owner boundary is identified and recorded for ISS-260 before closing.

## Notes
- 2026-07-05: Split from ISS-257.
- 2026-07-05: Current failure symptom: render-world lighting checks for
  directional shadow maps and cascades pass, while the runtime counter for
  resolved directional shadow resources in the volumetric fog pass does not.
- 2026-07-05: Started diagnosis after ISS-258 closed. Bevy's volumetric fog
  pass consumes directional shadow textures through `MeshViewBindGroup`, while
  mgstudio currently relies on the active renderer `GpuPassState` carrying the
  directional shadow texture from the preceding main pass into the volumetric
  fog draw.

## Close Notes
- 2026-07-05: The texture id loss was narrowed to mgstudio's local ownership
  boundary, not an external dependency. Bevy inserts `ViewShadowBindings` on
  the view, builds `MeshViewBindGroup` from those bindings, and
  `volumetric_fog` consumes `MeshViewBindGroup` directly. Mgstudio now passes
  the current `Render3dViewShadowBindings` into the volumetric fog pass and
  forwards the point/directional shadow texture ids explicitly to
  `draw_mesh3d_volumetric_fog`, so the renderer no longer infers the
  volumetric fog shadow texture from stale previous-pass shadow fields.
- 2026-07-05: Added the runtime counter
  `render_3d_volumetric_fog_view_shadow_binding_resources` and updated
  `scrolling_fog: runtime volumetric fog pass receives directional shadow
  resources` to prove the `scrolling_fog` shadow plan has a real directional
  shadow target and cascades and that those bindings reach volumetric fog host
  draw input.
- 2026-07-05: Updated the renderer white-box gate
  `renderer: volumetric fog resolves explicit view shadow texture identities`
  so fallback and real directional shadow texture identities are distinguished
  without reading `GpuPassState`.
- 2026-07-05: Validation:
  `moon -C mgstudio-engine test render/renderer --target native --release --filter '*volumetric fog resolves explicit view shadow texture identities*'`
  passed with `Total tests: 1, passed: 1, failed: 0`.
- 2026-07-05: Validation:
  `moon -C mgstudio-engine test examples/3d/scrolling_fog --target native --release --filter '*runtime volumetric fog pass receives directional shadow resources*'`
  passed with `Total tests: 1, passed: 1, failed: 0`.
- 2026-07-05: ISS-260 remains open for the broader source-shape follow-up:
  mgstudio still does not expose Bevy's `MeshViewBindGroup` as a first-class
  render-world component, even though the directional shadow texture path for
  this pass is now explicit and non-fallback.
